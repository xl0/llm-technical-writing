Rust for experienced C, Python, and TypeScript programmers

Reading time: about 18–20 minutes. This is a map of Rust’s important ideas, not a syntax catalogue. You already understand pointers, stacks, heaps, and types. The new territory is making ownership and aliasing part of the compiler’s job.

Rust offers C-like control over representation and allocation, with memory safety in safe code and no tracing garbage collector. Its distinguishing feature is not “everything is immutable” or “no pointers.” It is that APIs describe who owns a value, who may access it, and for how long.

That buys freedom from use-after-free, double-free, and data races—assuming the unsafe code underneath your abstractions is sound. It does not prevent memory leaks, deadlocks, logical bugs, or all panics.

1. Get oriented: Cargo and a little syntax

Cargo is the standard build tool, dependency manager, and test runner:

cargo new hello
cd hello
cargo run
cargo test
cargo fmt
cargo clippy
cargo build --release

cargo new creates a package with a Cargo.toml manifest and src/main.rs. A library normally starts at src/lib.rs. A crate is a compilation unit: a package can contain a library crate and binary crates. Cargo resolves dependencies and records selected versions in Cargo.lock.

Use cargo check for fast compiler feedback without producing a final executable. Development builds favor compilation speed and debugging; release builds enable optimization. clippy adds lint checks beyond the compiler’s diagnostics.

A small program:

fn magnitude(x: i64) -> i64 {
    // The final expression is the return value: no semicolon.
    if x < 0 { -x } else { x }
}

fn main() {
    let x = -12;                    // Type inferred from its use below.
    let mut calls: usize = 0;        // Reassignment requires `mut`.
    calls += 1;
    println!("{} after {calls} call", magnitude(x));
}

println! is a macro; ! distinguishes macro invocation from function calls. Formatting uses {} for display and {:?} for debug output, not C format strings.

Rust is expression-oriented: if, match, and blocks can produce values. A semicolon usually discards an expression’s result, leaving the block’s value as (), the unit type. return exists and is useful for early exits.

A few differences worth catching immediately:

  • let makes a binding immutable by default. This is a local access rule, not a promise that an entire object graph can never change.
  • Integer types include i32, u64, and pointer-sized usize/isize. Container lengths and indexes use usize.
  • There is no implicit truthiness or general implicit numeric conversion. Conditions must be bool.
  • as is not a checked conversion: an integer cast can truncate. Use u8::try_from(n) when failure matters.
  • Integer overflow normally panics in debug builds and wraps in release builds; profiles can change this. Use checked_add, wrapping_add, or saturating_add to specify intent. Signed overflow is not C-style undefined behavior.

That last point applies to our magnitude: negating i64::MIN cannot fit in i64. Rust prevents memory unsafety, not bad arithmetic specifications.

2. Ownership: destruction without a garbage collector

Start with C’s informal rule: “this function takes ownership of the allocation; don’t free it afterward.” Rust makes that rule enforceable.

let a = String::from("hello");
let b = a;                       // Ownership moves to b.
// println!("{a}");              // Error: a was moved.
println!("{b}");

A String owns a growable UTF-8 allocation. Conceptually, its handle contains a pointer, length, and capacity. Moving it transfers the handle and responsibility for the allocation; it does not deep-copy the text. The compiler prevents further use of the old binding.

Think of the two models this way:

C pointer assignment:    a ──┐
                            ├── allocation   (ownership is your convention)
                         b ──┘

Rust String move:        a [unusable]
                         b ──── allocation   (b now owns it)

When the owning value goes out of scope, Rust runs its destructor. String releases its buffer; Vec<T> drops its elements and frees its allocation. You can implement the Drop trait for your own resource cleanup. Files and locks use the same idea. This is often called RAII, even though you do not need C++ experience to use it.

Destruction normally happens at scope exit, not at the owner’s last use. It also happens during panic unwinding, but not when the process aborts. Cleanup that can fail, such as flushing output, may need an explicit method whose error you handle.

Function calls follow the same ownership rules:

fn consume(text: String) {
    println!("{text}");
} // text is dropped here

let message = String::from("hello");
consume(message);
// message is no longer usable.

But integers behave differently:

let a = 42_u32;
let b = a;
println!("{a} {b}");             // Both are usable.

Types implementing Copy are copied instead of moved. Integers, booleans, and many small value types qualify. String and Vec<T> do not: duplicating their owning handles would cause double-free.

For a deliberate duplicate, use .clone(). Cloning a String copies its text; cloning a reference-counted handle only adds another owner. Clone means “explicit duplication,” not necessarily “deep copy” or “cheap.”

This is not “stack types copy, heap types move.” Ownership is a type-level property. Moving a struct can transfer its inline fields and several owned allocations together.

3. Borrowing: access without ownership transfer

Most functions should not consume their arguments. They borrow instead:

fn byte_len(text: &str) -> usize {
    text.len()
}

fn add_exclamation(text: &mut String) {
    text.push('!');
}

let mut greeting = String::from("hello");
let n = byte_len(&greeting);
add_exclamation(&mut greeting);
println!("{greeting}: originally {n} bytes");

&T is a shared reference. &mut T is an exclusive reference that permits mutation. References are non-owning, must remain valid, and cannot be null.

The central rule is:

For overlapping access to the same data, allow shared references or an exclusive mutable reference—not both.

While an exclusive borrow is in use, you cannot access the borrowed data through a competing route. The compiler can distinguish disjoint fields and supports reborrowing, so this is more precise than “one pointer to an entire object, forever.”

Why restrict aliasing even in a single thread?

let mut names = vec![String::from("Ada")];
let first = &names[0];
names.push(String::from("Grace")); // Error: conflicts with borrow.
println!("{first}");

push might reallocate the vector, invalidating first. C permits you to express this bug. Rust rejects the overlapping borrow. Move the println! before push and the program is valid: the shared borrow is no longer needed when mutation begins.

This is an important distinction: a borrow often ends at its last use, while an owned resource is usually dropped at scope exit. You rarely need braces solely to shorten a borrow.

References themselves are values. Shared references are Copy; mutable references are not, because duplicating unrestricted exclusive access would break the rule. Many function calls implicitly make a shorter reborrow of a mutable reference, so passing one to a helper does not necessarily consume your ability to use it afterward.

Owned containers versus borrowed views

These pairs appear everywhere:

Owning type Borrowed view Meaning
String &str Owned UTF-8 text versus a view of text
Vec<T> &[T] Growable array versus a slice of elements
Vec<T> &mut [T] Exclusive access to existing elements, without resizing
Box<T> &T / &mut T Owned heap value versus borrowed access

A slice is conceptually a pointer plus a length, not a copied array. Prefer &[T] over &Vec<T> in an API that only needs to read elements; it accepts vectors, arrays, and slices. Prefer &str over &String for the same reason. Dereference coercions let &String become &str automatically at suitable call sites.

Rust strings are UTF-8, not arrays of fixed-width characters. text.len() counts bytes. .chars() yields Unicode scalar values, which still are not necessarily user-perceived characters. text[0] is forbidden; a byte-range slice such as &text[0..2] panics if its endpoints are not valid UTF-8 boundaries. Use byte APIs when your protocol is genuinely byte-oriented.

4. Lifetimes describe relationships, not timers

The compiler must prove that references do not outlive what they reference. Most lifetime information is inferred:

fn first_word(text: &str) -> &str {
    text.split_whitespace().next().unwrap_or("")
}

The returned view borrows from the input. The caller cannot destroy or incompatibly mutate the input while that result is still being used.

When a function returns one of multiple possible borrows, the relationship may need spelling out:

fn longer<'a>(left: &'a str, right: &'a str) -> &'a str {
    if left.len() >= right.len() { left } else { right }
}

Read 'a as: “the returned reference is valid for a region during which both input references are valid.” The caller can supply inputs with different actual lifetimes; the compiler finds a compatible shorter region. The function signature does not reveal which input will win.

Annotations do not extend an allocation’s life, add reference counting, or generate runtime checks. This cannot work:

// Does not compile, regardless of lifetime annotations.
fn broken<'a>() -> &'a str {
    let local = String::from("temporary");
    &local
}

Return String instead: move the owned value to the caller.

A struct storing a borrowed view also records that relationship:

struct Token<'a> {
    text: &'a str,
    byte_offset: usize,
}

This says a Token cannot be used beyond the lifetime of its borrowed text. It does not say the token owns that text.

&'static str, used by string literals, refers to text valid for the whole program. A bound such as T: 'static means the type contains no borrowed data with a shorter lifetime. An owned String satisfies it and can still be dropped immediately. Do not read 'static as “this object is immortal.”

Design advice: start with owned fields. Introduce borrowed fields when sharing a view has a clear benefit. Lifetime-heavy designs often come from trying to reproduce a C pointer graph before deciding who owns its nodes.

5. Types model alternatives, not just layouts

Structs group fields, and impl blocks attach behavior:

#[derive(Debug, Clone)]
struct User {
    name: String,
    visits: u64,
}

impl User {
    fn new(name: String) -> Self {
        Self { name, visits: 0 }
    }

    fn visit(&mut self) {
        self.visits += 1;
    }

    fn into_name(self) -> String {
        self.name
    }
}

Self names the implementing type. Notice how receivers document access: &self borrows, &mut self borrows exclusively, and self consumes. User::new is an ordinary associated function, not special constructor syntax. derive generates implementations of eligible traits.

Rust’s enum is a tagged union, closer to a TypeScript discriminated union than a C enum:

enum Event {
    Quit,
    Key(char),
    Paste { text: String },
}

fn handle(event: Event) {
    match event {
        Event::Quit => println!("bye"),
        Event::Key(c) => println!("key: {c}"),
        Event::Paste { text } => println!("paste: {text}"),
    }
}

match is exhaustive. Add a variant and the compiler identifies matches needing an update, unless a wildcard already covers it. Matching an owned enum can move its payload; match &event when you want to inspect it without consuming it. if let handles a single interesting pattern without a full match.

Two foundational enums are conceptually:

// Already provided by the standard library; do not redefine them.
enum Option<T> { None, Some(T) }
enum Result<T, E> { Ok(T), Err(E) }

Option<T> expresses absence. Result<T, E> expresses success or failure. There is no implicit nullable reference and no unchecked “possibly missing” access as in loosely typed Python. Handling the alternative is explicit in the type.

Rust does not generally promise C-compatible layouts for structs or enums. Use #[repr(C)] when a C-compatible layout is required, and ensure the fields themselves are appropriate for the ABI. A Rust String is not a C string.

6. Errors are values; ? is early return

A function with an expected failure path normally returns Result:

use std::{fs, io, num::ParseIntError, path::Path};

#[derive(Debug)]
enum PortError {
    Read(io::Error),
    Parse(ParseIntError),
}

fn read_port(path: &Path) -> Result<u16, PortError> {
    let text = fs::read_to_string(path).map_err(PortError::Read)?;
    let port = text.trim().parse::<u16>().map_err(PortError::Parse)?;
    Ok(port)
}

parse::<u16>() explicitly supplies a generic type argument; the syntax is nicknamed the turbofish. Often the surrounding context makes it unnecessary.

For Result, expression? means roughly:

let value = match expression {
    Ok(value) => value,
    Err(error) => return Err(error.into()),
};

It propagates failure out of the current function or closure, converting the error when a suitable From implementation exists. Our map_err calls explicitly turn the underlying errors into PortError variants. ? also works with Option in functions returning Option, propagating None; it does not automatically convert absence into an error. Use .ok_or(...) or .ok_or_else(...) for that.

There are no ordinary throw/catch exceptions. panic! signals an unrecoverable condition or programming error; unwinding can run destructors, but panics are not the normal error-return mechanism. A build can use aborting panics instead.

.unwrap() and .expect("reason") extract success or panic. They are reasonable in tests and for clearly justified invariants, not as default handling for network responses or user input. Likewise, indexing a vector can panic; .get(index) returns an Option<&T>.

Libraries often expose structured error enums that callers can inspect. Applications may prefer an error wrapper with context. The standard Box<dyn std::error::Error> is a convenient heterogeneous error return; crates such as thiserror and anyhow reduce boilerplate for different use cases.

7. Traits: interfaces, generic constraints, and dispatch

A trait describes behavior:

trait Describe {
    fn describe(&self) -> String;
}

impl Describe for User {
    fn describe(&self) -> String {
        format!("{}: {} visits", self.name, self.visits)
    }
}

fn show<T: Describe>(value: &T) {
    println!("{}", value.describe());
}

Unlike TypeScript’s structural interfaces, trait implementation is explicit. Unlike C++, Rust does not have class inheritance. Reuse comes from composition, trait implementations, and default trait methods.

Generic functions such as show normally use static dispatch: the compiler generates specialized code for concrete types. This is monomorphization. It permits inlining but can increase compile time and binary size.

Use a trait object when runtime polymorphism is appropriate:

fn show_dynamic(value: &dyn Describe) {
    println!("{}", value.describe());
}

&dyn Describe conceptually carries a data pointer and a vtable pointer. Box<dyn Describe> owns such a value; Vec<Box<dyn Describe>> can hold different implementing types. Only traits meeting dyn-compatibility rules support this form; for example, methods with their own type parameters generally cannot be dynamically dispatched.

impl Trait in an argument is convenient generic-bound syntax. In a return position it usually hides one concrete type chosen by the implementation, rather than returning arbitrary runtime alternatives. -> impl Iterator<Item = u8> is not the same as -> Box<dyn Iterator<Item = u8>>.

Traits also organize familiar operations: Iterator, IntoIterator, From, TryFrom, Default, Display, Debug, and Drop. Coherence rules restrict where implementations can be written: generally, the trait or implementing type must be local to your crate. Wrap a foreign type in a local “newtype” when you need your own behavior.

8. Iterators and closures retain ownership rules

Rust’s iterator pipelines look Pythonic but typically compile into specialized loops:

let numbers = vec![1, 2, 3, 4];
let squares: Vec<i32> = numbers
    .iter()
    .copied()
    .filter(|n| *n % 2 == 0)
    .map(|n| n * n)
    .collect();

assert_eq!(squares, vec![4, 16]);

The key distinction is what gets yielded:

  • .iter() borrows elements, yielding &T.
  • .iter_mut() borrows elements exclusively, yielding &mut T.
  • .into_iter() on an owned Vec<T> consumes it, yielding T.

for item in collection uses IntoIterator. Thus for x in &values borrows, while for x in values consumes an owned vector. The receiver matters: calling .into_iter() on a borrowed collection need not consume the underlying collection.

Adapters such as map and filter are lazy. collect, sum, or a loop actually drives them. Type inference flows both ways: the Vec<i32> annotation tells collect which container to build.

Closures borrow or move captures according to how they use them. move || ... forces captures to be taken by value, which is useful when work outlives its current scope. Capturing a reference by value still captures only a reference; it does not extend the referent’s life.

Fn, FnMut, and FnOnce describe how a closure may be called: through shared access, exclusive access, or by consuming it. Every closure supports FnOnce; closures that do not consume captures can support repeated calls. A move closure is not necessarily callable only once.

9. Shared ownership, threads, and async

Not everything forms a simple ownership tree. Rust has explicit tools for the other cases:

Type Purpose
Box<T> One owner of a heap-allocated value
Rc<T> Reference-counted shared ownership within one thread
Arc<T> Atomically reference-counted shared ownership across threads
RefCell<T> Borrow-rule checking at runtime, typically within one thread
Mutex<T> / RwLock<T> Synchronized access to shared data

Rc and Arc do not automatically permit mutation. Rc<RefCell<T>> and Arc<Mutex<T>> combine ownership with an access policy. RefCell can panic on a conflicting borrow; try_borrow variants report failure instead. A mutex guard unlocks when dropped.

These are forms of interior mutability: controlled mutation behind shared references. They explain why &T is not a universal “deeply frozen” promise. Ownership cycles through Rc or Arc can leak; use Weak for non-owning back-links.

Thread safety is also expressed through traits:

  • Send: ownership of a value can safely move between threads.
  • Sync: shared references to a value can safely cross thread boundaries.

These are usually inferred from fields. Rc is not thread-safe; Arc is designed for shared ownership across threads, but does not make an unsafe-to-share payload magically safe. Safe Rust prevents data races, not deadlocks or incorrect ordering of otherwise synchronized operations.

Async is a separate concern. Calling an async fn returns a future; the function body executes as that future is polled, not immediately as with the start of a JavaScript async function. .await permits suspension. Futures do not automatically run on new threads or imply parallel execution.

The standard library defines the core machinery, but an ecosystem runtime such as Tokio normally supplies scheduling and async I/O. An async runtime does not make blocking file or CPU work nonblocking. Avoid holding a blocking mutex guard across .await; choose scoped locking or suitable async synchronization. Dropping a future generally cancels further polling, so partially completed external effects still require careful design.

10. Unsafe, FFI, and performance boundaries

unsafe does not disable Rust’s type checker or borrow checker. It permits specific operations whose safety the compiler cannot establish, including dereferencing raw pointers and calling unsafe functions.

A safe abstraction may use unsafe internals. Its implementer must ensure every permitted safe use upholds the required invariants. Incorrect unsafe code can make otherwise safe callers exhibit undefined behavior.

Raw pointers, *const T and *mut T, resemble C pointers: they may be null or dangling, and lack reference lifetime guarantees. Merely possessing a raw pointer is not the same as dereferencing it. Converting it into a reference requires satisfying Rust’s validity and aliasing requirements, not just checking for null.

For C interop, establish contracts for layout, calling convention, ownership, buffer length, and cleanup. Use tools such as CString/CStr for nul-terminated strings. Do not assume Rust panics and foreign exceptions can safely cross arbitrary ABI boundaries.

Performance should otherwise feel familiar: contiguous vectors, inline struct fields, explicit allocations, and specialized generic code. Safe indexing checks bounds, though optimization often eliminates redundant checks. Iterator abstractions can optimize as well as hand-written loops; “zero-cost abstraction” is a design goal, not a guarantee that every program is optimal.

Measure release builds before reaching for unchecked indexing or unsafe pointer arithmetic.

11. A complete small program

Put this in src/main.rs. It reads unsigned integers, one per nonempty line, and prints their maximum. It combines borrowing, iterators, typed parsing, error propagation, and explicit absence handling:

use std::{error::Error, fs};

fn maximum(text: &str) -> Result<Option<u64>, std::num::ParseIntError> {
    let mut best: Option<u64> = None;

    for line in text.lines().map(str::trim).filter(|s| !s.is_empty()) {
        let value = line.parse::<u64>()?;
        best = Some(match best {
            Some(previous) => previous.max(value),
            None => value,
        });
    }

    Ok(best)
}

fn main() -> Result<(), Box<dyn Error>> {
    let path = std::env::args_os().nth(1).ok_or_else(|| {
        std::io::Error::new(std::io::ErrorKind::InvalidInput, "expected a path")
    })?;

    let text = fs::read_to_string(path)?;
    match maximum(&text)? {
        Some(value) => println!("{value}"),
        None => println!("no numbers"),
    }
    Ok(())
}

#[cfg(test)]
mod tests {
    use super::maximum;

    #[test]
    fn handles_numbers_empty_input_and_errors() {
        assert_eq!(maximum("12\n\n 7\n25\n").unwrap(), Some(25));
        assert_eq!(maximum(" \n").unwrap(), None);
        assert!(maximum("not a number").is_err());
    }
}

Run it with cargo run -- numbers.txt; arguments after -- go to your program. Run the test with cargo test.

Result<Option<u64>, E> deliberately distinguishes three outcomes: invalid input, valid input with no numbers, and a maximum. No sentinel value or exception convention is required. The function borrows the file contents and allocates no per-line strings.

mod defines a module; use brings names into scope rather than textually including a file. Items are private by default; pub exposes them subject to their containing modules’ visibility. #[cfg(test)] includes the test module only when building tests. Integration tests live separately under tests/ and exercise your library’s public interface.

12. How to become productive

When the compiler rejects an ownership design, ask these questions in order:

  1. Who should own this value? Move it there instead of borrowing a temporary.
  2. Does this function need ownership, mutation, or only observation? Choose T, &mut T, or &T accordingly.
  3. Is this borrow genuinely needed across the mutation? Reorder work or extract a small owned result first.
  4. Is shared ownership fundamental? Use Rc/Arc, or use indexes/IDs into an owning collection for graph-like structures.
  5. Would a small clone simplify the design? It can be a good trade. Understand its cost rather than treating cloning as failure.

Do not respond to every diagnostic by adding lifetimes, wrapping everything in Arc<Mutex<_>>, or reaching for unsafe. Read compiler suggestions, but preserve the ownership model you actually want.

The central shift from C is making resource and aliasing contracts executable by the compiler. From Python and TypeScript, it is learning to distinguish an owned value from a borrowed view, and static polymorphism from runtime indirection. Once those distinctions become natural, most Rust syntax is just notation around them.

Rust for C, Python, and TypeScript Experts

Estimated reading time: 15–20 minutes

If you already know C, Python, and TypeScript, you have lived on both sides of a classic language trade-off:

  • In C, you get exact control over memory layout, stack frames, cache locality, and zero runtime overhead—paid for by manual lifetime tracking in your head and Undefined Behavior (UB) landmines (use-after-free, double free, buffer overruns, iterator invalidation, data races).
  • In Python and TypeScript, you get expressive type systems (TS discriminated unions, generics), high-level ergonomics (Python iterators, closures, async/await), and memory safety—paid for by boxing values on the heap, pointer chasing, and garbage collection or reference counting.

Rust’s core thesis is that this trade-off is a false dichotomy. Rust compiles TypeScript-grade algebraic types and Python-grade iterator/closure pipelines directly down to C’s flat memory model—with no garbage collector and no hidden object headers—by enforcing two invariants at compile time:

  1. Affine Ownership + Deterministic Destruction (Drop): Every value has a single owner (typically a stack frame or enclosing struct). Assignment moves ownership by copying stack bytes (memcpy) and statically invalidating the old binding. When the owner goes out of scope, the compiler inserts cleanup code deterministically—like C’s goto cleanup or Python’s with block, but automatic and impossible to forget.
  2. Aliasing XOR Mutability (&T vs. &mut T): At any point in execution, a memory location may have either any number of shared read-only pointers (&T) or exactly one exclusive mutable pointer (&mut T)—never both simultaneously.

2. Physical Memory Layout, Moves, and Strings

If you think of Rust variables like Python or JS variables, the borrow checker will feel arbitrary. Think of them like C structs on the stack, and every rule clicks immediately.

Stack by Default, Explicit Heap

When you write:

struct Point {
    x: f64,
    y: f64,
}

Point is 16 contiguous bytes on the stack—no PyObject header, no V8 hidden class pointer, no heap allocation. One C difference: By default (#[repr(Rust)]), the compiler is free to reorder struct fields to eliminate alignment padding. When passing structs across a C ABI boundary or memory-mapping hardware/network headers, annotate the struct with #[repr(C)].

Move vs. Copy vs. Clone: What let b = a; Really Does

Consider how String (a growable UTF-8 buffer) is laid out on a 64-bit machine. It is a 24-byte stack header { ptr: *mut u8, len: usize, cap: usize } owning a heap buffer—identical to Vec<u8>.

What happens when you assign let s2 = s1;?

  • In Python/TypeScript: s2 = s1 copies an 8-byte pointer. Both bindings alias the same heap allocation.
  • In C: s2 = s1 copies the 24-byte struct on the stack. Now both s1.ptr and s2.ptr point to the same heap buffer. If both clean up at scope exit, you get a double-free.
  • In Rust: let s2 = s1; copies the 24-byte header on the stack (memcpy, not a deep heap copy) and statically marks s1 as uninitialized (moved). Only s2 will run its destructor (Drop::drop) when the scope exits.
fn main() {
    let s1 = String::from("rust!"); // allocates 5 bytes on heap
    let s2 = s1;                    // 24-byte stack memcpy; s1 is now dead
    // println!("{s1}");            // COMPILE ERROR: borrow of moved value: `s1`

    let s3 = s2.clone();            // Explicit deep heap allocation + copy
    println!("{s2} and {s3}");

    let x: i32 = 42;
    let y = x;                      // i32 implements `Copy`: x remains valid
    println!("{x} and {y}");
} // s3 and s2 drop here, each freeing its own heap buffer

Types fall into two categories: - Move types (the default): String, Vec<T>, Box<T>, File, MutexGuard, and any struct/enum you define unless you opt in. Assignment transfers ownership. - Copy types: Pure bit-blobs that own no external heap/OS resources—integers (i32, u64, usize), floats (f64), bool, char, shared references (&T), raw pointers (*const T), fixed-size arrays of Copy types ([u8; 32]), and user structs annotated with #[derive(Copy, Clone)]. For Copy types, b = a is a bitwise copy and a stays usable.

Mental shortcut: In Rust, memcpy is the only implicit copy. Deep copies (Clone::clone) are always explicit in source code, and constructors do not exist (Foo { a, b } is just literal struct initialization).

String vs. &str and Vec<T> vs. &[T] (Fat Pointers)

A C programmer constantly passes (const uint8_t *buf, size_t len) pairs around. Rust bakes that pair into a first-class primitive called a slice:

  • &[T] is a 16-byte fat pointer (ptr: *const T, len: usize) borrowing a contiguous view of Ts anywhere in memory (stack array, heap Vec<T>, or static binary data).
  • &str is simply a &[u8] carrying a compile-time invariant that the bytes are valid UTF-8.
  • Notice: Rust strings are not null-terminated (they can contain interior \0 bytes, and taking a substring &s[1..4] is $O(1)$ with zero allocation—unlike C’s strncpy).

API rule of thumb: Never write fn process(s: &String) or fn sum(v: &Vec<i32>). Always accept the slice view instead:

fn first_word(s: &str) -> &str {
    match s.find(' ') {
        Some(idx) => &s[..idx],
        None => s,
    }
}

fn main() {
    let owned = String::from("hello world");
    let word1 = first_word(&owned);        // &String automatically coerces to &str (via Deref)
    let word2 = first_word("literal str"); // &'static str works directly too
    assert_eq!(word1, "hello");
    assert_eq!(word2, "literal");
}

Why can’t you index a string with s[0]? Because UTF-8 is variable-width (1 to 4 bytes per Unicode code point). s[i] would either be an $O(n)$ scan (like Python 2/UTF-8 scan) or return a raw byte that splits a multi-byte character (like C), or expose UTF-16 surrogates (like JS/TS). Rust forces you to say what you want: - s.as_bytes()[0] — $O(1)$ raw u8 byte access. - &s[0..4] — $O(1)$ UTF-8 sub-slice (panics at runtime if byte index 4 falls mid-codepoint). - s.chars() — iterator over 4-byte Unicode scalar values (char).

3. The Borrow Checker & Lifetimes ('a) Without Mysticism

Instead of transferring ownership every time you call a function, you pass references (&T and &mut T). At the machine level, a reference is just a non-null C pointer (*const T or *mut T, or a 2-word fat pointer for slices/trait objects).

At compile time, references obey Aliasing XOR Mutability—which you can picture as a zero-cost compile-time pthread_rwlock_t attached to every variable:

Why C’s const T* Is Weak and Rust’s &T / &mut T Is Strong

In C, const int *p only means "I promise not to mutate *p through p"—nothing stops another pointer int *q in the same scope from mutating *p right underneath you. That is why C compilers cannot hoist loads across function calls without restrict.

In Rust: - &T (Shared Reference): Freeze the referent. You can copy &T freely (&T: Copy), handing out 100 readers, and Rust guarantees nobody is mutating the value anywhere. - &mut T (Mutable Reference): Exclusive access (&mut T is not Copy). While &mut T exists, nobody else can read or write the value—not even the original owner. Every &mut T automatically emits LLVM’s noalias attribute (a compiler-verified C restrict).

Classic C/C++ Footgun Caught at Compile Time

Every C and C++ programmer has written this bug in some disguise: holding a pointer into a dynamic array while appending to it:

fn main() {
    let mut buf = vec![10, 20, 30];
    let first = &buf[0]; // Shared borrow (&i32) of `buf` starts
    buf.push(40);        // ERROR: `push` takes `&mut self` (may realloc() and free old heap buffer!)
    println!("{first}"); // Shared borrow still live here -> `first` would dangle!
}

rustc rejects this with a surgical diagram of the conflict:

error[E0502]: cannot borrow `buf` as mutable because it is also borrowed as immutable
 --> src/main.rs:4:5
  |
3 |     let first = &buf[0];
  |                  --- immutable borrow occurs here
4 |     buf.push(40);
  |     ^^^^^^^^^^^^ mutable borrow occurs here
5 |     println!("{first}");
  |                ----- immutable borrow later used here

Notice Non-Lexical Lifetimes (NLL): if you move println!("{first}"); above buf.push(40);, the program compiles! A borrow’s lifetime lasts only until its last use in the control-flow graph, not until the closing } of the block.

Lifetimes ('a) Demystified

Lifetimes ('a, 'src, 'static) are the most misunderstood syntax in Rust. Two facts eliminate 90% of the confusion:

  1. Lifetimes do not exist at runtime. They are erased before LLVM codegen; you cannot "extend" a value’s lifetime by changing 'a.
  2. 'a is just a generic parameter for scopes. Just as TypeScript uses <T> to tell the typechecker how an output type relates to input types, Rust uses <'a> to tell the borrow checker which input reference an output reference borrows from.

When a function takes one reference and returns a reference (fn first_word(s: &str) -> &str), the compiler infers the relationship automatically (lifetime elision). You only write 'a explicitly in two situations:

Situation 1: Returning a reference that could come from multiple inputs.

// Says: "The returned slice is valid for the intersection ('a) of x's and y's borrows."
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() >= y.len() { x } else { y }
}

Situation 2: Zero-copy structs that hold references. In C, storing a const char* inside a parsed struct is fast (zero allocations) but terrifying (if the backing buffer is freed first, every struct field dangles). In Rust, you parameterize the struct over the buffer’s lifetime 'src:

#[derive(Debug, PartialEq)]
struct Header<'src> {
    name: &'src str,  // Borrows directly from the input buffer
    value: &'src str, // Zero heap allocations!
}

fn parse_header<'src>(line: &'src str) -> Option<Header<'src>> {
    let (name, value) = line.split_once(':')?;
    Some(Header {
        name: name.trim(),
        value: value.trim(),
    })
}

The 'src annotation proves at compile time that no Header<'src> instance can ever outlive the line buffer it slices into.

4. Expressions, Algebraic Types (enum), and Pattern Matching

Everything Is an Expression

Rust is an expression-oriented language. if, match, { ... } blocks, and even loop evaluate to values. - A block’s value is its final expression without a trailing semicolon. - Adding a semicolon turns an expression into a statement whose value is ()—the unit type (a zero-byte type sizeof(()) == 0 that unifies C’s void and Python’s None without needing special compiler cases).

let port: u16 = if let Ok(val) = std::env::var("PORT") {
    val.parse().unwrap_or(8080) // no semicolon -> yields value
} else {
    8080
};

struct + impl: Explicit Receivers Like Python, Static Layout Like C

Rust has no class keyword and no implementation inheritance (extends). Data lives in struct or enum; methods live in impl blocks. Like Python, methods declare self explicitly—using ownership modes to express what the method needs:

  • &self (short for self: &Self): shared read-only borrow (most methods).
  • &mut self: exclusive mutable borrow.
  • self: consumes the receiver by value (great for state transitions, e.g., connection.close(self) or builder.build(self)—calling any method on connection afterward is a compile error!).

enum: C union Efficiency + TypeScript Discriminated Union Safety

In TypeScript, discriminated unions are a superpower:

type Frame =
  | { kind: "ping" }
  | { kind: "text"; payload: string }
  | { kind: "binary"; flags: number; data: Uint8Array };

In Rust, enum gives you the exact same algebraic expressiveness and exhaustiveness checking, but laid out in flat inline memory like a C struct { uint8_t tag; union { ... }; }:

enum Frame {
    Ping,
    Text(String),
    Binary { flags: u8, payload: Vec<u8> },
}

And you cannot read a variant’s payload without pattern-matching its discriminant first:

fn payload_size(frame: &Frame) -> usize {
    match frame {
        Frame::Ping => 0,
        Frame::Text(s) => s.len(),
        // Match specific field values + destructure + guard clauses:
        Frame::Binary { flags: 0x01, payload } => payload.len(),
        Frame::Binary { payload, .. } if !payload.is_empty() => payload.len() + 1,
        Frame::Binary { .. } => 0,
    }
}

When you only care about one variant—especially for early-return guard clauses—use if let or let ... else (where the else block must diverge via return, break, continue, or panic!):

fn handle_text(frame: &Frame) -> Result<&str, &'static str> {
    let Frame::Text(body) = frame else {
        return Err("expected a Text frame");
    };
    Ok(body) // `body: &String` is bound in the outer scope!
}

Niche Optimization: Why Option<&T> Costs Zero Extra Bytes

Rust has no NULL for safe references (&T, &mut T, Box<T>). When a value may be absent, you wrap it in Option<T>:

pub enum Option<T> {
    None,
    Some(T),
}

A C programmer immediately asks: "Does Option<&T> double my pointer size from 8 bytes to 16 bytes with a tag + padding?" No. Because &T, &mut T, Box<T>, fn() pointers, and NonZeroU64 have invalid bit patterns (0x0 is never a valid reference), the compiler uses 0x0 to represent None (niche optimization). size_of::<Option<&T>>() is 8 bytes, and Option<&T> has the exact same ABI representation as a nullable C pointer const T*!

5. Error Handling: Result<T, E> and the ? Operator

Rust does not use exceptions for recoverable errors (unlike Python/TS, where any function call might invisibly unwind the stack), nor does it use C’s error codes + out-pointers (where forgetting to check a return value silently corrupts state).

Instead, fallible functions return Result<T, E>:

#[must_use] // Compiler warns if you ignore a returned Result!
pub enum Result<T, E> {
    Ok(T),
    Err(E),
}

The ? Operator: C’s goto cleanup Perfected

In C, clean resource management in a multi-step function requires a cascade of if ((err = step()) != 0) goto cleanup; labels. In Rust, the postfix ? operator unwraps Ok(val) or immediately returns Err(From::from(err)) to the caller—while RAII Drop automatically cleans up every local resource in reverse declaration order:

use std::fs::File;
use std::io::{self, Read};
use std::path::Path;

#[derive(Debug)]
enum ConfigError {
    Io(io::Error),
    MissingPort,
    InvalidPort(std::num::ParseIntError),
}

// Implementing `From` lets `?` automatically convert sub-errors into `ConfigError`
impl From<io::Error> for ConfigError {
    fn from(e: io::Error) -> Self { Self::Io(e) }
}
impl From<std::num::ParseIntError> for ConfigError {
    fn from(e: std::num::ParseIntError) -> Self { Self::InvalidPort(e) }
}

fn read_port(path: &Path) -> Result<u16, ConfigError> {
    let mut raw = String::new();
    // 1. Opens File; 2. Reads into `raw`; 3. Closes File descriptor on drop—even on Err!
    File::open(path)?.read_to_string(&mut raw)?;

    let Some(port_str) = raw.lines().find_map(|l| l.strip_prefix("port=")) else {
        return Err(ConfigError::MissingPort);
    };
    Ok(port_str.trim().parse::<u16>()?)
}

Ecosystem standard: In real projects, nobody hand-writes impl From boilerplate for errors: - Libraries use thiserror (#[derive(thiserror::Error, Debug)] with #[from] and #[error("...")] attributes) so callers get strongly typed error enums. - Applications/CLIs use anyhow (anyhow::Result<T> + .context("failed to read config")?), which works like an ergonomic, type-erased error with backtraces. - panic! (and .unwrap() / .expect("reason")) is reserved for programmer bugs / invariant violations (like an out-of-bounds array index v[99]) or tests/prototypes.

6. Polymorphism: Traits, Monomorphization, and Fat-Pointer Vtables

Rust replaces classes, interfaces, and C function-pointer tables with traits. A trait defines shared behavior—similar to a TypeScript interface or Python Protocol, plus default method implementations and associated types.

trait Codec {
    fn encode(&self, out: &mut Vec<u8>);

    // Default method implementation:
    fn to_bytes(&self) -> Vec<u8> {
        let mut buf = Vec::new();
        self.encode(&mut buf);
        buf
    }
}

The Orphan Rule (Coherence): You can implement a trait for a type if and only if either the trait or the type is defined in your crate. You can implement your Codec trait for Rust’s u64 or String, or implement Rust’s Display trait for your Packet struct—but you cannot implement Display for Vec<u8>. This guarantees linking two crates can never cause conflicting trait implementations.

Static Dispatch (<T: Trait>) vs. Dynamic Dispatch (&dyn Trait)

In Python, Java, or C++ (virtual), polymorphism is decided when defining the class, and every instance carries an object header / vptr in memory.

In Rust, structs have zero vtable overhead in memory, and the caller/API chooses between compile-time monomorphization and runtime vtable dispatch:

use std::io::Write;

// 1. STATIC DISPATCH (Monomorphized — zero runtime overhead, inlined per concrete W)
//    `w: &mut impl Write` is syntactic sugar for `<W: Write>(w: &mut W)`
fn write_header_static<W: Write>(w: &mut W) -> std::io::Result<()> {
    w.write_all(b"MAGIC\n")
}

// 2. DYNAMIC DISPATCH (16-byte fat pointer `(data_ptr, vtable_ptr)` — one compiled function)
fn write_header_dynamic(w: &mut dyn Write) -> std::io::Result<()> {
    w.write_all(b"MAGIC\n")
}

// 3. HETEROGENEOUS COLLECTION via Box<dyn Write> (fat pointer owning heap allocation)
fn flush_all(writers: &mut [Box<dyn Write>]) -> std::io::Result<()> {
    for w in writers {
        w.flush()?;
    }
    Ok(())
}

7. Closures & Zero-Cost Iterators: Python Ergonomics, C Assembly

In Python, list comprehensions and generator pipelines ((x * x for x in nums if x > 0)) are a joy to write, but each step crosses the bytecode interpreter and allocates PyObjects. In Rust, iterator pipelines look almost identical—and compile down to the exact same (or faster, bounds-check-elided SIMD) machine code as a hand-rolled C for loop:

fn top_positive_squares(nums: &[i64], limit: usize) -> Vec<i64> {
    nums.iter()               // yields &i64
        .copied()             // yields i64 (by value)
        .filter(|&x| x > 0)   // lazy adapter struct: Filter<...>
        .map(|x| x * x)       // lazy adapter struct: Map<Filter<...>>
        .take(limit)          // lazy adapter struct: Take<Map<Filter<...>>>
        .collect()            // consumes pipeline into Vec<i64> (type inferred from return!)
}

The Three Iteration Modes

Collections provide three iterator methods corresponding to the three ownership modes: 1. v.iter() (or for x in &v) $\rightarrow$ yields shared references &T. 2. v.iter_mut() (or for x in &mut v) $\rightarrow$ yields mutable references &mut T. 3. v.into_iter() (or for x in v) $\rightarrow$ consumes v and yields owned values T.

How Closures Work Without a Garbage Collector (Fn, FnMut, FnOnce)

In Python and TypeScript, a closure (x => x + threshold) heap-allocates a scope/cell object to hold captured variables. In Rust, a closure |x| x + threshold compiles into an anonymous stack struct containing the captured variables! By default, the compiler captures variables in the least restrictive way needed, classifying the closure into a hierarchy of three traits:

  • Fn (subtrait of FnMut): Captures state via shared reference &T. Can be called any number of times, even concurrently across threads.
  • FnMut (subtrait of FnOnce): Captures state via mutable reference &mut T. Can be called repeatedly to mutate its environment (e.g., a counter closure).
  • FnOnce: Consumes captured values by moving them out of the closure struct. Can only be called once.

Adding the move keyword (move |x| ...) forces the closure struct to take ownership of its captured variables by value instead of borrowing them from the enclosing stack frame—which is required whenever a closure outlives the current stack frame (such as spawning a thread or returning a closure).

8. When the Borrow Checker Says No: Smart Pointers & Interior Mutability

A strict tree of single owners works for 90% of data structures, but what if you are building a graph, an LRU cache, shared state across callbacks, or mutating a lazy cache inside a read-only &self method?

Rust does not ban shared ownership or mutation through shared references. Instead, it requires you to pick the exact runtime pointer and synchronization mechanism via standard library wrapper types:

Type Ownership Thread-Safe? What It Does & Runtime Cost
Box<T> Single owner Yes (if T: Send) Heap allocation (malloc/free) owned by a single 8-byte stack pointer. Used for recursive types, large structs, or Box<dyn Trait>.
Rc<T> Shared (1..N) No (!Send) Single-threaded reference counting (like Python’s ob_refcnt). Cloning increments a non-atomic counter (usize) and yields a shared &T. Use rc::Weak<T> to break cycles.
Arc<T> Shared (1..N) Yes (Send + Sync) Atomic Reference Counting (atomic_fetch_add). Standard way to share heap data across threads or async tasks.
Cell<T> Interior mutability No (!Sync) Zero-cost mutation through &Cell<T> by moving/copying values in and out (.get(), .set()). Never hands out a &T into the cell, so pointers can never dangle.
RefCell<T> Interior mutability No (!Sync) Moves the borrow checker (&T XOR &mut T) to runtime via a borrow counter. .borrow() returns Ref<T>; .borrow_mut() returns RefMut<T>. Panics if both coexist at runtime.
Mutex<T> / RwLock<T> Interior mutability Yes (Sync) OS/futex lock wrapping the data T itself. Calling .lock() blocks and returns a MutexGuard<T> that derefs to &mut T and unlocks automatically on drop.

Why Rust’s Mutex<T> is a revelation for C programmers: In C, a pthread_mutex_t lock; sits next to struct state data; by mere comment convention—nothing stops a new teammate from touching data without locking lock, or forgetting pthread_mutex_unlock on an early return. In Rust, the data lives inside Mutex<State>. You literally do not have a pointer to State until you call let mut guard = mutex.lock().unwrap();, and you cannot forget to unlock it because guard’s Drop releases the lock at scope exit. Need shared mutable state across single-threaded callbacks? Combine Rc<RefCell<T>>. Across threads? Combine Arc<Mutex<T>>.

9. Fearless Concurrency & Poll-Based async/await

Send, Sync, and Scoped Threads

How does Rust prevent data races at compile time? Through two auto-implemented marker traits: - Send: A type is Send if ownership of it can safely be transferred to another thread. Almost everything is Send except non-atomic Rc<T>, raw pointers *const T, and OS thread-local handles (like MutexGuard). - Sync: A type is Sync if it is safe for multiple threads to hold &T simultaneously (T is Sync $\iff$ &T is Send). Primitives, immutable structs, Mutex<T>, and AtomicU64 are Sync; Cell<T> and RefCell<T> are !Sync.

If you try to capture an Rc<T> inside thread::spawn(move || ...), the program fails to compile because Rc<T> is not Send—preventing non-atomic reference count corruption before your code ever runs.

Even better, std::thread::scope lets you spawn threads that directly borrow local stack variables without Arc or heap allocation, because the scope guarantees all spawned threads join before the scope exits:

use std::sync::Mutex;
use std::thread;

fn parallel_sum(data: &[u64]) -> u64 {
    let (left, right) = data.split_at(data.len() / 2);
    let total = Mutex::new(0u64);

    // `thread::scope` joins all child threads before returning, so threads
    // can safely borrow `left`, `right`, and `&total` from the parent stack!
    thread::scope(|s| {
        for chunk in [left, right] {
            let total_ref = &total;
            s.spawn(move || {
                let partial: u64 = chunk.iter().sum();
                *total_ref.lock().unwrap() += partial;
            });
        }
    });

    total.into_inner().unwrap() // Consumes Mutex with zero locking once threads have joined
}

How Rust async/await Differs from TypeScript and Python

In TypeScript and Python (asyncio), async/await is built around an implicit global runtime and heap-allocated Promise / Task objects. Rust’s async/await is designed for systems programming where even an embedded microcontroller with no heap can run async code:

Four critical differences from TypeScript and Python:

  1. Futures are cold (lazy): In TypeScript, calling const p = fetch(url); starts the network request immediately. In Rust, calling let fut = fetch(url); does nothing except construct the initial FetchFuture::Unpolled enum on the stack. Work only advances when you .await it or pass it to tokio::spawn(...).
  2. State machines, not heap callbacks: Each async fn compiles into a single flat enum whose size is the largest set of variables live across any .await point. Waiting on a composite future (tokio::join!(a, b)) requires zero extra heap allocations.
  3. Bring your own executor: Rust’s standard library defines the Future trait, not the event loop (epoll/kqueue/io_uring reactor). In practice, Tokio is the de facto standard multi-threaded work-stealing runtime (#[tokio::main]).
  4. Cancellation is just Drop: Dropping a future (e.g., via tokio::time::timeout(dur, fut).await) stops polling it at its current .await point and runs Drop on its live local variables. And because worker threads multiplex thousands of tasks, never block an async thread with heavy CPU work or synchronous syscalls—offload those to tokio::task::spawn_blocking or rayon.

10. Escape Hatches & Tooling: unsafe, C FFI, and Cargo

What unsafe Actually Does (and Doesn’t Do)

Safe Rust is intentionally conservative: if the compiler cannot prove a memory access is sound, it rejects the program. When you are writing an OS kernel, a custom allocator, SIMD intrinsics, or C FFI, you use an unsafe { ... } block.

Crucial misconception: unsafe does not turn off the borrow checker (&T and &mut T are still checked normally inside unsafe!). It only unlocks five specific operations: 1. Dereferencing raw pointers (*const T and *mut T). 2. Calling an unsafe fn (including C extern functions and intrinsics). 3. Implementing an unsafe trait (like Send or Sync). 4. Accessing or modifying a mutable static variable. 5. Accessing fields of a raw C-style union.

The idiomatic Rust pattern is encapsulating a small, auditable unsafe block inside a 100% safe function signature. Here is how the standard library’s slice::split_at_mut splits one mutable slice &mut [T] into two disjoint mutable slices (&mut [T], &mut [T])—something the borrow checker cannot prove on its own because it only sees slice borrowed mutably twice:

pub fn split_at_mut<T>(slice: &mut [T], mid: usize) -> (&mut [T], &mut [T]) {
    let len = slice.len();
    assert!(mid <= len, "mid out of bounds"); // Safe runtime check upholds invariant!
    let ptr = slice.as_mut_ptr();             // *mut T raw pointer

    // SAFETY: We asserted `0 <= mid <= len`, so `[0..mid)` and `[mid..len)`
    // are valid, initialized, and strictly non-overlapping sub-ranges.
    unsafe {
        (
            std::slice::from_raw_parts_mut(ptr, mid),
            std::slice::from_raw_parts_mut(ptr.add(mid), len - mid),
        )
    }
}

Notice the // SAFETY: comment convention: every unsafe block in serious Rust code documents the exact proof obligations that make Undefined Behavior impossible for any inputs passed to the outer safe function.

Rust for people who already know C, Python and TypeScript

A condensed introduction. About 15–20 minutes. Assumes you are fluent in C, Python and TypeScript; C++ is not required.

Rust is a compiled, statically typed systems language with no garbage collector and no runtime to speak of. It gives you C's control over memory and layout, a type system closer to TypeScript's (and richer), and an expression-oriented, iterator-heavy style that will feel familiar from Python. What makes it different from everything you already know is a single idea: the compiler tracks who owns every value and who is allowed to touch it, and it refuses to build programs where that bookkeeping doesn't add up. Most of this document is about that idea and its consequences. The rest is a tour of what you'd expect from a modern language, with pointers to where Rust differs from your intuitions.

This is current as of Rust 1.99 (September 2026), edition 2024.

1. Orientation

  • Toolchain. rustup installs and manages compilers. cargo is the build tool, package manager, test runner and doc generator; you will almost never invoke rustc directly. Packages are crates, published to crates.io, declared in Cargo.toml. cargo new foo && cd foo && cargo run is the whole hello-world ritual.
  • Releases. A new stable compiler every six weeks, with strong backward-compatibility guarantees. Editions (2015, 2018, 2021, 2024) let the language make small breaking syntax changes; crates on different editions interoperate freely, and cargo fix --edition migrates you.
  • Compilation model. Ahead-of-time to native code via LLVM. Monomorphized generics (like C++ templates, unlike TS or Python), so abstractions typically cost nothing at runtime. Compile times are the price, and they are noticeable.
  • No undefined behavior in safe code. Out-of-bounds indexing panics deterministically instead of corrupting memory. Integer overflow panics in debug builds and wraps in release builds (or use explicit wrapping_add, checked_add, saturating_add). Null does not exist; uninitialized reads cannot be expressed; data races are compile errors.
  • Panics vs errors. A panic is for bugs (like a failed assert): it unwinds the stack and, by default, kills the thread. Recoverable failures are ordinary return values of type Result. There are no exceptions.

2. Syntax in one screen

use std::collections::HashMap;

// Items: fn, struct, enum, trait, impl, mod, const, static, type, use.
const MAX_RETRIES: u32 = 3;                 // compile-time constant, inlined

fn mean(xs: &[f64]) -> Option<f64> {        // &[f64] is a slice: pointer + length
    if xs.is_empty() {
        return None;                        // early return needs `return`
    }
    let sum: f64 = xs.iter().sum();
    Some(sum / xs.len() as f64)             // last expression is the return value, no semicolon
}

fn main() {
    let x = 5;                              // immutable by default; type inferred as i32
    let mut count = 0u64;                   // `mut` opts into mutation; literal suffix fixes type
    let x = x * 2;                          // shadowing is normal and idiomatic
    count += 1;

    // Blocks are expressions. `if` is an expression. No ternary operator needed.
    let label = if x > 5 { "big" } else { "small" };

    // Loops: `loop` (infinite, can break with a value), `while`, `for` over anything iterable.
    let found = loop {
        count += 1;
        if count > 10 { break count * 2; }
    };
    for i in 0..3 { print!("{i} "); }       // ranges: 0..3 excludes 3, 0..=3 includes it
    for (k, v) in [("a", 1), ("b", 2)] { println!("{k}={v}"); }

    // Tuples, arrays (fixed size, stack), destructuring.
    let pair: (i32, &str) = (1, "one");
    let (n, name) = pair;
    let arr: [u8; 4] = [0; 4];              // four zeros; the length is part of the type

    let mut m: HashMap<&str, i32> = HashMap::new();
    m.insert("answer", 42);
    println!("{label} {found} {n} {name} {} {:?} {MAX_RETRIES}", arr.len(), mean(&[1.0, 2.0]));
}

Things to notice coming from your three languages:

  • Types go after the name (x: i32), like TypeScript. Inference is local-but-strong: you annotate function signatures, almost nothing inside bodies.
  • Integer types are explicit and fixed-width: i8..i128, u8..u128, isize/usize (pointer-sized; indices are usize), f32, f64, bool, char (a 4-byte Unicode scalar, not a byte). No implicit numeric conversions, not even u8 → u32. You write as for lossy casts or .into() / try_into() for checked ones. This is tedious for about a week and then you stop writing integer bugs.
  • Statements vs expressions. A trailing ; turns an expression into a statement whose value is (), the unit type. Forgetting one on a function's last line is the first compile error everyone hits.
  • println! with a ! is a macro. Macros are hygienic and type-checked after expansion; vec![1, 2, 3], format!, assert_eq! and #[derive(...)] are the ones you'll see constantly. Format strings capture local variables ({x}), {:?} prints debug representations, {:#?} pretty-prints.
  • Namespaces use ::. Methods use .. Both exist on types (String::new()) and values (s.len()).

3. Ownership: the part that is actually new

C gives you manual lifetime management. Python and TypeScript give you a garbage collector. Rust gives you a third thing: lifetime management that is manual in principle but checked, and mostly inferred, by the compiler.

3.1 Every value has exactly one owner

fn main() {
    let s = String::from("hello");  // s owns a heap buffer
    let t = s;                      // ownership MOVES to t; s is now dead
    // println!("{s}");             // error[E0382]: borrow of moved value: `s`
    println!("{t}");
}                                   // t goes out of scope -> buffer freed here, deterministically

A String is three machine words on the stack (pointer, capacity, length) owning a heap buffer, exactly as you'd write it in C:

Assigning let t = s is a plain 24-byte copy of the handle, and then the compiler statically forbids further use of s. No reference counting, no copying of the heap bytes, no double free. This is "move semantics", and unlike C++ it is the default and it is enforced: a moved-from variable is simply gone.

When the owner goes out of scope, the value is dropped: its destructor (the Drop trait) runs, recursively, in reverse declaration order. Files close, locks release, memory frees, at a point you can read off the source. This is RAII without the C++ baggage, and it is why Rust code rarely has defer/finally/with blocks: the cleanup is attached to the type.

3.2 Copy vs Clone

Moving everything would be miserable for integers. Types that are plain bits (i32, f64, bool, char, raw pointers, shared references, tuples/arrays of such) implement the marker trait Copy: assignment copies and the source stays valid, just like C. Anything that owns a resource (String, Vec<T>, Box<T>, File) is move-only. If you want a deep copy, you ask for it explicitly: let t = s.clone();. Expensive copies are therefore always visible in the source, which is a real readability win over Python, where you can never tell from b = a whether aliasing is about to bite you.

3.3 Functions take and give ownership

fn consume(v: Vec<i32>) -> usize { v.len() }           // takes ownership; v is dropped at the end
fn produce() -> Vec<i32> { vec![1, 2, 3] }             // returns ownership to the caller

fn main() {
    let v = produce();
    let n = consume(v);
    // v is gone here. If you still need it, pass a reference instead (next section).
    println!("{n}");
}

Returning a Vec or String from a function does not copy the heap data. The three-word handle moves out; the buffer stays where it is. Rust has no hidden copies.

4. Borrowing: references with rules

Passing ownership around for every function call would be absurd, so Rust has references. A reference is a non-null, always-valid pointer, with two flavors and one rule.

fn len(s: &String) -> usize { s.len() }        // shared (immutable) borrow
fn shout(s: &mut String) { s.push_str("!"); } // exclusive (mutable) borrow

fn main() {
    let mut s = String::from("hi");
    let n = len(&s);         // lend s out, read-only
    shout(&mut s);           // lend s out, read-write; `&mut` must be written at the call site too
    println!("{s} {n}");     // s still owned here
}

The rule: at any point in the program, a value has either any number of shared references &T or exactly one exclusive reference &mut T, never both. And every reference must be proven to not outlive the value it points at.

The compiler component that enforces this is the borrow checker. It operates purely at compile time; references are ordinary pointers at runtime, and &T to a u8 is one machine word, same as uint8_t*.

Why this exact rule? Because "shared XOR mutable" is precisely the condition under which:

  • No use-after-free is possible. You cannot hold a &T to something that gets dropped, and you cannot mutate (e.g. reallocate a Vec) while someone holds a reference into it. The classic C bug of taking a pointer into a buffer and then reallocing it is a compile error. So is Python's "dictionary changed size during iteration", except it fails at compile time rather than at runtime.
  • No data races are possible. Two threads mutating the same thing requires two &mut to it, which cannot exist. Section 9 shows how this makes concurrency pleasant.
  • The optimizer gets restrict for free, everywhere, provably correct.

The cost is that some programs you know are fine are rejected, and you have to restructure. Three patterns cover most of these:

fn main() {
    let mut v = vec![1, 2, 3];

    // 1. Shorten borrows: compute what you need, drop the reference, then mutate.
    let first = v[0];           // i32 is Copy, so this is a value, not a borrow
    v.push(first);

    // 2. Use indices or iterators that hand out one element at a time.
    for x in v.iter_mut() { *x *= 2; }   // iter_mut yields &mut i32, one at a time, safely

    // 3. Split borrows: the standard library gives you non-overlapping views.
    let (left, right) = v.split_at_mut(2);
    left[0] += right[0];
    println!("{v:?}");
}

Since 2018 the checker understands non-lexical lifetimes: a borrow ends at its last use, not at the closing brace. Most "obviously fine" code just works.

4.1 Lifetimes

Sometimes the compiler needs you to say how long a reference lives, usually when a function returns a reference and it is ambiguous which input it borrows from:

// "The output lives at least as long as `a`." `'a` is a lifetime parameter; it is a generic.
fn first_word<'a>(a: &'a str, _sep: &str) -> &'a str {
    a.split(' ').next().unwrap_or("")
}

struct Parser<'src> {       // a struct holding a reference must say how long it lives
    input: &'src str,
    pos: usize,
}

Lifetime annotations never change what the program does; they are type-level documentation that lets the checker verify the body against the signature and callers against the signature without looking at the body. The language elides them in the common cases (one reference in, one reference out; methods returning references to self), so you write them far less often than you'd fear. 'static means "lives for the whole program", which string literals do.

The honest summary: you will fight the borrow checker for a couple of weeks. Then the rules become how you think, and you'll notice you have stopped writing a whole class of bug in C and Python too.

5. Data modeling: structs, enums, pattern matching

5.1 Structs

#[derive(Debug, Clone, PartialEq)]       // auto-generate trait impls; very common
struct Point { x: f64, y: f64 }

struct Meters(f64);                      // tuple struct: a newtype with zero runtime cost

impl Point {                             // methods live in impl blocks, separate from the data
    fn origin() -> Self { Point { x: 0.0, y: 0.0 } }          // associated fn (no self): a "static"
    fn dist(&self, other: &Point) -> f64 {                     // &self: borrows the receiver
        ((self.x - other.x).powi(2) + (self.y - other.y).powi(2)).sqrt()
    }
    fn translate(&mut self, dx: f64, dy: f64) { self.x += dx; self.y += dy; }  // &mut self
    fn into_tuple(self) -> (f64, f64) { (self.x, self.y) }     // self by value: consumes
}

fn main() {
    let mut p = Point { x: 1.0, y: 2.0 };
    p.translate(1.0, 1.0);
    let q = Point { x: 5.0, ..p };       // struct update syntax, like JS spread
    println!("{:?} {} {}", q, p.dist(&q), Meters(3.0).0);
}

Layout is C-like (the compiler may reorder fields unless you say #[repr(C)]), there is no inheritance, no constructors (just functions returning Self), no implicit this. The receiver type (self, &self, &mut self) tells the caller exactly what the method does to ownership, and auto-referencing means you call all three as p.method().

5.2 Enums are tagged unions that actually work

This is the feature that C programmers most wish they had and TypeScript programmers will recognize as discriminated unions, done with compiler support:

enum Shape {
    Circle { r: f64 },
    Rect { w: f64, h: f64 },
    Point,
}

fn area(s: &Shape) -> f64 {
    match s {                                       // match must be exhaustive
        Shape::Circle { r } => std::f64::consts::PI * r * r,
        Shape::Rect { w, h } => w * h,
        Shape::Point => 0.0,
    }   // add a variant later and every non-exhaustive match becomes a compile error
}

Variants can carry data; the enum is stored as a tag plus a union sized for the largest payload, like you'd hand-write in C, but you cannot read the wrong arm.

Two enums from the standard library structure the entire language:

enum Option<T> { Some(T), None }          // replaces null
enum Result<T, E> { Ok(T), Err(E) }        // replaces exceptions

Option<&T> and Option<Box<T>> compile down to a nullable pointer (the "niche" optimization), so there is no cost over C, just the inability to forget the null check. match and friends work on all of them:

fn parse_port(s: &str) -> Result<u16, std::num::ParseIntError> {
    s.trim().parse::<u16>()               // parse is generic over the target type
}

fn main() {
    let input = Some("8080");

    // `if let` for one pattern
    if let Some(s) = input {
        println!("got {s}");
    }

    // `let else` for "destructure or bail"
    let Some(s) = input else { return };

    // Combinators, in the Python/TS functional style
    let port = parse_port(s).ok().filter(|p| *p > 1024).unwrap_or(3000);

    // match with guards, ranges, bindings, nesting
    let msg = match port {
        0 => "reserved",
        p @ 1..=1023 if p % 2 == 0 => "even privileged",
        1..=1023 => "privileged",
        _ => "user",
    };
    println!("{port} {msg}");
}

5.3 Error handling and ?

Errors are values. The ? operator unwraps an Ok/Some or early-returns the Err/None, converting the error type via From on the way out:

use std::fs;
use std::io;

fn read_config(path: &str) -> Result<u16, Box<dyn std::error::Error>> {
    let text = fs::read_to_string(path)?;   // io::Error -> Box<dyn Error> automatically
    let port: u16 = text.trim().parse()?;   // ParseIntError -> Box<dyn Error>
    Ok(port)
}

fn main() -> io::Result<()> {               // main can return Result; Err prints and exits 1
    match read_config("app.port") {
        Ok(p) => println!("port {p}"),
        Err(e) => eprintln!("config error: {e}"),
    }
    Ok(())
}

Compare to the alternatives you know: C's if (ret < 0) goto cleanup; is what ? desugars to, minus the forgetting. Python's exceptions are invisible in signatures; here the Result<T, E> return type tells you exactly what can fail. TypeScript's throw is untyped; E is typed. In applications, the anyhow crate gives you a convenient catch-all error with context chaining; in libraries, thiserror derives proper error enums. .unwrap() and .expect("msg") panic on Err/None; they are fine in prototypes and tests and a code smell in library code.

6. Traits and generics

A trait is an interface, in roughly the Haskell typeclass sense: a set of methods a type can implement, declared separately from the type. TypeScript interfaces are structural (anything with the right shape matches); Rust traits are nominal (you must write impl Trait for Type), but you can implement your traits for other people's types and other people's traits for yours.

use std::fmt;

trait Area {
    fn area(&self) -> f64;
    fn describe(&self) -> String {                 // default method, overridable
        format!("shape with area {:.2}", self.area())
    }
}

struct Square(f64);
impl Area for Square { fn area(&self) -> f64 { self.0 * self.0 } }

impl fmt::Display for Square {                     // a std trait; gives you `{}` formatting
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result { write!(f, "Square({})", self.0) }
}

// Generic function: monomorphized per concrete T, like a C++ template, zero overhead.
fn total_area<T: Area>(items: &[T]) -> f64 { items.iter().map(|s| s.area()).sum() }

// `impl Trait` in argument position is sugar for a generic. In return position it hides the type.
fn biggest(items: &[impl Area]) -> f64 { items.iter().map(Area::area).fold(0.0, f64::max) }

// Trait object: dynamic dispatch through a vtable. Needed for heterogeneous collections.
fn print_all(items: &[Box<dyn Area>]) { for s in items { println!("{}", s.describe()); } }

fn main() {
    let sq = [Square(1.0), Square(2.0)];
    println!("{} {} {}", total_area(&sq), biggest(&sq), sq[0]);
    let mixed: Vec<Box<dyn Area>> = vec![Box::new(Square(3.0))];
    print_all(&mixed);
}

Points worth internalizing:

  • Bounds are mandatory. fn f<T>(x: T) can do nothing with x except move it. To call .area(), you must say T: Area. This is C++ concepts / TS generic constraints, but required rather than optional, so error messages point at the call site, not three layers of template instantiation deep. Multiple bounds: T: Area + Clone, or a where clause.
  • Operators are traits. a + b is Add::add(a, b). Indexing is Index, == is PartialEq, for loops are IntoIterator, {} is Display, {:?} is Debug. Implement them for your types and they behave like built-ins.
  • #[derive] writes the boring impls for you: Debug, Clone, Copy, PartialEq, Eq, Hash, PartialOrd, Ord, Default. Third-party crates extend this; serde's #[derive(Serialize, Deserialize)] is the canonical example and the reason JSON handling in Rust is about as pleasant as in TypeScript.
  • dyn Trait vs generics. Default to generics (static dispatch, inlining). Reach for Box<dyn Trait> or &dyn Trait when you need a heterogeneous collection or want to cut compile times and code size. A &dyn Trait is a fat pointer: data pointer plus vtable pointer, two words.
  • Associated types and generic traits. Iterator has type Item;, which is why .map(...) knows what it yields. You'll meet impl Iterator<Item = u32> in return types constantly.
  • Marker traits have no methods and encode facts: Copy (bitwise copyable), Send (safe to move to another thread), Sync (safe to share between threads), Sized. The compiler derives Send/Sync structurally and uses them to reject data races at compile time.

7. Iterators and closures

Iterators are the idiomatic replacement for most loops, and unlike Python generators they compile to the same machine code as the hand-written loop. Chains are lazy until a consumer (collect, sum, for, count, fold, any...) pulls from them.

fn main() {
    let words = ["apple", "bob", "kayak", "rust", "level"];

    let palindromes: Vec<String> = words
        .iter()                                    // yields &&str
        .filter(|w| w.chars().eq(w.chars().rev()))  // closure; `|args| body`
        .map(|w| w.to_uppercase())
        .collect();                                // target type drives what gets built

    let total_len: usize = words.iter().map(|w| w.len()).sum();
    let longest = words.iter().max_by_key(|w| w.len());          // Option<&&str>
    let indexed: Vec<(usize, &str)> = words.iter().copied().enumerate().collect();
    let by_len = words.iter().fold(std::collections::HashMap::new(), |mut m, w| {
        m.entry(w.len()).or_insert_with(Vec::new).push(*w);
        m
    });

    println!("{palindromes:?} {total_len} {longest:?} {indexed:?} {by_len:?}");
}

Three iterator flavors over a collection, mirroring the three receiver types: iter() borrows (&T), iter_mut() borrows mutably (&mut T), into_iter() consumes (T). for x in &v / &mut v / v is shorthand for each.

Closures capture their environment by reference, mutable reference or move, inferred from use (the move keyword forces by-value). Each closure is its own anonymous type implementing Fn, FnMut or FnOnce, depending on whether it reads, mutates or consumes captures; functions that take closures are generic over those traits, so there's no allocation unless you box them. This is the mechanism behind the "zero-cost" claim: a .map(|x| x + 1) is inlined like a macro, not called through a function pointer.

To write your own iterator, implement one method:

struct Countdown(u32);
impl Iterator for Countdown {
    type Item = u32;
    fn next(&mut self) -> Option<u32> {
        if self.0 == 0 { None } else { self.0 -= 1; Some(self.0 + 1) }
    }
}
fn main() { let v: Vec<_> = Countdown(3).collect(); assert_eq!(v, [3, 2, 1]); }

All seventy-odd adapters (zip, take_while, flat_map, peekable, chunks, windows, rev...) come for free.

8. Strings, slices and collections

Rust has two string types and the distinction trips everyone up for a day:

Type What it is C analogue Python/TS analogue
String owned, growable, heap, UTF-8 char* you malloced + len + cap str (as an owned value)
&str borrowed view: pointer + length into UTF-8 bytes const char* + size_t, no NUL a string slice / substring without copy

String literals are &'static str. Functions should take &str (a &String coerces to it automatically). Indexing s[i] is not allowed, because i would be a byte index into UTF-8 and might split a character; use s.chars(), s.bytes(), or byte-range slicing &s[0..3] which panics if you cut a code point. This is the correct design and nobody enjoys it on day one.

The same owned/borrowed pair exists for everything: Vec<T> / &[T], PathBuf / &Path, Box<T> / &T. Write APIs in terms of the borrowed form.

Collections in std::collections: Vec<T> (dynamic array, your default), VecDeque<T>, HashMap<K, V> and HashSet<T> (SipHash by default, DoS-resistant and slower than you'd expect; swap the hasher if it matters), BTreeMap/BTreeSet (ordered), BinaryHeap. Vec<T> is contiguous and &v[..] is a slice you can hand to C.

9. Smart pointers, shared state, concurrency

The ownership rules above describe a tree: each value has one owner. Real programs sometimes need graphs, shared caches, or two threads looking at the same thing. The standard library provides escape hatches that move the checking from compile time to runtime in a controlled way, rather than giving up on it.

Type Purpose Cost
Box<T> Owned heap allocation. Recursive types, large values, trait objects. one pointer
Rc<T> Shared ownership, single-threaded. Reference-counted; freed when count hits 0. Immutable contents. non-atomic count
Arc<T> Same, thread-safe. atomic count
Cell<T> / RefCell<T> Interior mutability: mutate through a shared &. RefCell enforces the borrow rules at runtime and panics on violation. Single-threaded. a flag
Mutex<T> / RwLock<T> Interior mutability across threads. The lock owns the data; you can only reach T through the guard, so forgetting to lock is impossible. a lock
atomics AtomicUsize etc., same as C11. —

The idioms are Rc<RefCell<T>> for shared mutable state in one thread and Arc<Mutex<T>> across threads. These are deliberately a little noisy; the noise marks where the compile-time guarantees stop and runtime checks begin. Rust has no cycle collector, so Rc cycles leak; break them with Weak<T>.

Threads:

use std::sync::{Arc, Mutex, mpsc};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0u64));
    let (tx, rx) = mpsc::channel();

    let handles: Vec<_> = (0..4).map(|id| {
        let counter = Arc::clone(&counter);        // each thread gets its own Arc handle
        let tx = tx.clone();
        thread::spawn(move || {                    // `move`: the closure owns counter and tx
            for _ in 0..1000 { *counter.lock().unwrap() += 1; }  // guard unlocks when dropped
            tx.send(id).unwrap();
        })
    }).collect();
    drop(tx);                                      // close our copy so rx knows when all senders are gone

    for h in handles { h.join().unwrap(); }
    let finished: Vec<u32> = rx.iter().collect();
    println!("{} from {:?}", *counter.lock().unwrap(), finished);
}

If you forget the Mutex and try to share a plain u64 mutably, or you try to send an Rc to another thread, the compiler rejects the program, citing Send/Sync. "Fearless concurrency" is marketing, but it is accurate marketing: the class of bug where two threads scribble on the same memory simply does not compile. std::thread::scope lets threads borrow from the parent's stack frame without Arc, when their lifetime is bounded.

Async. Rust has async fn and .await, structurally like TypeScript's. The difference is that the language ships only the Future trait and the syntax; the executor is a library (tokio is the de facto standard, smol and async-std exist). Futures are inert state machines that do nothing until polled, there is no implicit global event loop, and you choose single- or multi-threaded runtimes. It is the right tool for network services with many connections and the wrong tool for CPU work or simple programs; threads are cheaper to reason about and perfectly fast.

10. Modules, crates, tooling

  • A crate is a compilation unit: a binary (src/main.rs) or a library (src/lib.rs). A package (Cargo.toml) holds one library and any number of binaries; a workspace holds many packages.
  • Modules form a tree inside a crate. mod net; pulls in src/net.rs or src/net/mod.rs. Everything is private by default; pub exports it to the parent, pub(crate) to the crate. use crate::net::Socket; imports. There is no header/implementation split and no circular-import problem, since the whole crate is one unit.
  • Dependencies go in Cargo.toml: serde = { version = "1", features = ["derive"] }. Cargo.lock pins exact versions; commit it for binaries. Cargo handles diamond dependencies by allowing multiple semver-incompatible versions of a crate side by side.
  • Testing is built in: #[test] functions anywhere, cargo test. #[cfg(test)] mod tests { ... } at the bottom of a file is the convention; integration tests go in tests/. Code examples in /// doc comments are compiled and run as tests, so docs don't rot.
  • Everything else: cargo fmt (one canonical style, no bikeshedding), cargo clippy (several hundred lints, genuinely educational), cargo doc --open, cargo bench, cargo build --release (always benchmark release; debug builds are 10–50× slower).
  • Attributes #[...] annotate items: #[derive], #[test], #[inline], #[cfg(target_os = "linux")], #[repr(C)], #[allow(dead_code)]. Think decorators, resolved at compile time.

11. unsafe and talking to C

Safe Rust cannot dereference raw pointers, call C functions, access static mut, or implement Send/Sync by hand. Inside an unsafe { } block it can, and you take on the obligation to uphold the invariants the compiler normally checks. Nothing else changes: the borrow checker still runs, types still check. unsafe is a grep-able marker saying "audit here", and the standard library's own Vec is built on it.

unsafe extern "C" {
    fn strlen(s: *const std::ffi::c_char) -> usize;    // declare a C symbol
}

#[unsafe(no_mangle)]
pub extern "C" fn rust_add(a: i32, b: i32) -> i32 { a + b }   // export one, callable from C

fn main() {
    let c_string = std::ffi::CString::new("hello").unwrap();   // NUL-terminated, owned
    let n = unsafe { strlen(c_string.as_ptr()) };              // caller promises the pointer is valid
    println!("{n}");
}

The C ABI is first-class: #[repr(C)] structs match C layout, raw pointers *const T / *mut T are exactly C pointers (nullable, no lifetime, arithmetic via .add()/.offset()), bindgen generates declarations from headers and cbindgen goes the other way. Rust is used as a drop-in for individual C translation units in the Linux kernel, Android, Chromium, Windows and Firefox precisely because this boundary is cheap and the memory-safety rules compose across it. Calling Python from Rust and vice versa is well served by PyO3, and Rust is what most of the fast Python packages you've used lately are written in (pydantic-core, polars, ruff, uv). For TypeScript, napi-rs and wasm-bindgen cover Node and the browser.

13. Idioms and gotchas, condensed

  • Clone to make it compile, then remove the clones that matter. Starting out, .clone() your way past borrow errors; it's correct, just sometimes slow. Profile later. Most never matter.
  • Take &str, &[T], impl AsRef<Path> as arguments; return owned String, Vec<T>. Borrow in, own out.
  • Don't store references in structs until you have to. struct Foo<'a> infects every user with a lifetime. Owned data or Rc/Arc is usually the right trade.
  • Shadowing is your friend: let x: u32 = x.parse()?; is normal.
  • match on tuples to handle combinations: match (a.is_some(), b) { (true, 0) => ..., ... }.
  • Prefer if let/let else/?/combinators over unwrap. Every unwrap is a potential panic you've chosen to accept.
  • Integers don't coerce. v.len() is usize; mixing it with an i32 needs as or try_from. Use usize for anything that indexes.
  • The compiler's error messages are the tutorial. They name the rule, show the span, and usually suggest the fix. Read them fully; rustc --explain E0502 gives a page on each.
  • Dead ends you'll hit: self-referential structs (use indices or Pin), linked lists (use Vec or VecDeque; if you insist, read Learning Rust With Entirely Too Many Linked Lists), returning a closure (impl Fn(i32) -> i32 or Box<dyn Fn>), mutating a collection while iterating it (collect the changes, apply after).

Rust for a C, Python, and TypeScript programmer

A 15–20 minute introduction. You already know how to program; this guide concentrates on what changes when you program in Rust. Examples use stable Rust and the 2024 edition. Deliberately rejected examples are marked compile_fail; most other snippets illustrate individual items rather than complete programs.

1. The central bargain

Think of Rust as C-level control with a much stronger static contract. There is no required garbage collector, objects do not all live on the heap, and ordinary function calls need no interpreter. You choose representation, allocation, sharing, and indirection—but the compiler checks many obligations that C leaves to your discipline.

The important shift is not syntax. It is making ownership and access permissions part of your program's types and structure.

In C, a pointer rarely tells you whether you may free its target, retain it, mutate it, or use it concurrently. Rust distinguishes these cases. Safe Rust prevents dangling references, double frees, and data races. It does not promise freedom from memory leaks, deadlocks, incorrect algorithms, or panics. Those guarantees also depend on any underlying unsafe code honoring its contracts.

Three familiar-language analogies help, up to a point:

  • C: values, explicit layouts when requested, native compilation, predictable allocation. Unlike C, a normal reference comes with validity and aliasing requirements the compiler enforces.
  • Python: expressive collections and iteration, but no pervasive dynamic typing or implicit shared ownership of objects.
  • TypeScript: inference, generics, and discriminated unions, but Rust's types constrain actual runtime representation and access, not just a type-checking layer over JavaScript.

The new question to ask constantly is: who owns this value, and who currently has permission to access it?

2. Enough syntax and tooling to get started

Install the toolchain with rustup. Cargo handles builds, dependency resolution, tests, and packaging:

cargo new rust-tour --edition 2024
cd rust-tour
cargo run                 # debug build, then execute
cargo run --release       # optimized build
cargo check               # type/borrow checking without producing an executable
cargo test
cargo fmt
cargo clippy              # additional linting; install the component if needed

Cargo.toml is the package manifest; Cargo.lock records resolved dependencies. A crate is a compilation unit: usually a library or executable. A package can contain both. Dependencies are crates too; you normally add them with cargo add NAME.

An edition opts a crate into a set of language changes; it is not the compiler's version. Crates using different editions can interoperate.

Here is the basic shape:

fn classify(n: i32) -> &'static str {
    let magnitude = n.unsigned_abs();
    if magnitude < 10 { "small" } else { "large" }
}

fn main() {
    let count = 3;             // immutable binding; type inferred
    let mut total: i64 = 0;    // mutable binding; explicit type
    for n in 0..count {        // half-open range
        total += n as i64;
    }
    println!("{total}: {}", classify(count));
}

Key differences from C:

  • Blocks and if are expressions. A final expression without a semicolon supplies the block's value. Adding a semicolon generally changes that result to (), the unit type.
  • Function parameter and return types are explicit; local types are usually inferred.
  • i32, u64, f64, etc. have explicit widths. usize is the unsigned pointer-sized integer used for indexing.
  • Numeric conversions are not generally implicit. as can truncate or reinterpret numeric values; use checked conversions such as u8::try_from(n) when failure matters.
  • println!, vec!, and format! are macros, hence !. Rust macros operate on syntax; they are not C-style textual substitution.
  • There are no exceptions to declare or catch as part of ordinary error handling. More on that below.

mut belongs to a binding. It is not a universal promise that nothing reachable through an immutable binding can change: types with interior mutability deliberately provide controlled exceptions.

Project structure is not textual inclusion

src/main.rs is the usual executable root; src/lib.rs is the library root. Modules organize a crate's namespace. For example, mod parser; normally loads a child module from parser.rs or parser/mod.rs, relative to the declaring source file's module location. use crate::parser::parse; brings a path into scope; it does not include source text or execute a Python-style import.

Items are private by default. pub exposes them, subject to their enclosing modules' visibility; pub(crate) exposes them only inside the current crate. Struct fields have their own visibility, so a public struct can keep its representation private.

3. Ownership: assignment can consume a value

An owning value is responsible for its resources. When it is dropped, cleanup runs. For example, a String owns a growable UTF-8 buffer; a Vec<T> owns a contiguous buffer of elements.

let a = String::from("hello");
let b = a;                     // ownership moves to b
// println!("{a}");            // error: a was moved
println!("{b}");

The move does not duplicate the string's bytes. Conceptually, it transfers the small owning handle and makes the old binding unusable. The compiler may optimize away any physical handle copy.

This is very different from Python's b = a, where two names usually reference the same object. It is also different from copying a C struct containing an owning pointer, where both copies remain usable and you must prevent double-free yourself.

The same rule applies at function boundaries:

fn consume(text: String) {
    println!("{text}");
} // text is dropped here

let message = String::from("hello");
consume(message);
// message is no longer usable

Returning a value transfers ownership to the caller. Moving a resource into a struct transfers responsibility to that struct. Moves are the default, not special syntax.

Copy versus Clone

Some types implement Copy: integers, booleans, and other types that permit implicit duplication. For them, assignment leaves the original usable:

let x = 42;
let y = x;
println!("{x} {y}");

String and Vec<T> are not Copy. To duplicate a string's owned buffer, ask explicitly:

let a = String::from("hello");
let b = a.clone();

Clone does not universally mean “deep-copy everything.” Its meaning belongs to the type: cloning a String duplicates its buffer; cloning an Rc<T> creates another shared owner of the same allocation. Copy types are also Clone.

Destruction, not manual free

Rust calls Drop implementations automatically when values are dropped. Collections also drop their elements. This handles memory, files, lock guards, and other resources. You do not normally write free, and cleanup does not wait for a garbage collector.

You can release something early with drop(value), which consumes it. But do not use destruction as a reliable way to report fallible operations: explicitly flush or commit when failure matters. Aborting a process also bypasses normal cleanup.

C instinct to replace: instead of documenting “caller must free,” express ownership in the parameter and return types.

4. Borrowing: access without taking ownership

Most functions should not consume their inputs. They borrow them:

fn byte_length(text: &str) -> usize {
    text.len()
}

fn add_suffix(text: &mut String) {
    text.push('!');
}

let mut message = String::from("hello");
let length = byte_length(&message);
add_suffix(&mut message);
println!("{message}: originally {length} bytes");

&T is a shared reference. &mut T is an exclusive reference, normally used to mutate. Both are non-owning and must point to valid data; neither is nullable.

The working rule is:

For overlapping access to the same memory, allow shared references or an exclusive reference—not conflicting uses of both.

Through &T, ordinary data cannot be mutated. Through &mut T, you have exclusive access to the borrowed data, including protection from competing reads. Ownership remains elsewhere in both cases.

Why this restriction? Consider retaining a reference into a vector while growing it:

let mut values = vec![10, 20, 30];
let first = &values[0];
values.push(40);             // could reallocate, invalidating first
println!("{first}");         // so this program is rejected

C would let you manufacture a use-after-free. Rust rejects it before execution.

Borrows usually end at their last use, not at the closing brace:

let mut values = vec![10, 20, 30];
let first = &values[0];
println!("{first}");         // last use of first
values.push(40);             // now allowed

The checker tracks more than “one mutable reference in the entire program.” It can distinguish separate struct fields, and APIs such as slice.split_at_mut(i) safely produce two nonoverlapping mutable slices. When you know two runtime indices are distinct, the compiler may still need such an API to establish that fact.

Borrowing also explains a useful loop distinction:

let mut values = vec![1, 2, 3];
for x in &values { println!("{x}"); } // borrow elements as &i32
for x in &mut values { *x += 1; }     // borrow elements as &mut i32
for x in values { println!("{x}"); }  // consume vector, yielding elements
// values has been moved

The same syntax can borrow, mutate, or consume depending on the iterator source. Read the types, not just the punctuation.

5. Lifetimes: relationships, not manual memory management

A lifetime describes how long a borrow can validly be used. The compiler infers most of them:

fn first_word(text: &str) -> &str {
    text.split_whitespace().next().unwrap_or("")
}

This returns a view into the input, not a new string. The signature's elision rules connect the returned reference to the input reference. The caller cannot keep using the result after the backing data becomes invalid.

With multiple inputs, an explicit relationship may be necessary:

fn longer<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

Read this as: “for a shared borrow lifetime 'a, accept two string slices valid for that lifetime and return one valid for it.” The result cannot be used beyond the lifetime available from both inputs. The function does not promise which input it selects.

Annotations do not extend an object's life. They cannot make returning a reference to a local String legal. Return an owned String in that case.

A struct can hold a borrow:

struct Token<'a> {
    text: &'a str,
    offset: usize,
}

This represents a token whose text is backed by something else. It avoids copying, but makes the backing storage's lifetime a concern for users of Token. An owned String field is often a better initial design.

&'static str, the type of a string literal, can refer to data valid for the entire program. A T: 'static bound means T contains no borrows that limit it to a shorter lifetime—not that a value of T must remain alive forever. An owned String satisfies that bound and can still be dropped immediately.

When fighting the borrow checker: first simplify ownership. Choose one owner, shorten a borrow, return owned data, or separate mutation from inspection. Do not start by adding lifetime annotations everywhere.

6. Model data with structs, enums, and exhaustive matches

Structs are straightforward; methods live in impl blocks:

#[derive(Debug)]
struct Point {
    x: f64,
    y: f64,
}

impl Point {
    fn norm(&self) -> f64 {
        self.x.hypot(self.y)
    }

    fn translate(&mut self, dx: f64, dy: f64) {
        self.x += dx;
        self.y += dy;
    }
}

A method's receiver advertises its access: self consumes, &self borrows, &mut self borrows exclusively. Point::new(...), when provided, is an ordinary associated function, not a special constructor mechanism. derive generates implementations for supported traits.

Rust enums are tagged unions whose variants may carry different data:

enum Event {
    Quit,
    Key(char),
    Resize { width: u32, height: u32 },
}

fn describe(event: Event) -> String {
    match event {
        Event::Quit => String::from("quit"),
        Event::Key(c) => format!("key {c}"),
        Event::Resize { width, height } => format!("{width}×{height}"),
    }
}

Think TypeScript discriminated unions, but with a concrete native representation and exhaustive checking. Adding a variant forces relevant matches to be reconsidered, unless a wildcard arm already accepts it.

Two standard enums replace common C conventions:

enum Option<T> { None, Some(T) }
enum Result<T, E> { Ok(T), Err(E) }

These definitions illustrate types already provided by the standard library. Option<T> represents absence instead of a nullable ordinary reference; Result<T, E> represents an operation's success or failure. A Some(0) is distinct from None.

Use if let Some(value) = maybe_value { ... } when you only care about one pattern. Patterns can move contained values too: matching &event rather than event borrows its contents instead of consuming them.

There is no class inheritance. Prefer structs composed from other structs, enums for a closed set of alternatives, and traits for shared capabilities.

7. Errors are values; panics are a different mechanism

A fallible function normally returns Result:

use std::num::ParseIntError;

fn doubled(text: &str) -> Result<i32, ParseIntError> {
    let n = text.parse::<i32>()?;
    Ok(n.saturating_mul(2))
}

Here ? means: extract the Ok value, or return early with the error, converting it through From when needed. It is explicit propagation, not an exception thrown through arbitrary callers. The containing function must have a compatible return type. ? also propagates None inside an Option-returning function; it does not automatically turn an Option into a Result.

The ::<i32> spelling supplies a generic type argument at a call site; it is often nicknamed the turbofish.

Useful combinators:

  • map: transform a success/present value.
  • map_err: transform an error.
  • and_then: chain another fallible operation.
  • ok_or_else: turn absence into a lazily constructed error.
  • unwrap_or_else: supply a fallback by running a closure.

unwrap() and expect("reason") panic on None or Err. They are reasonable in tests and for genuinely established invariants, but are not a substitute for handling malformed input.

A panic signals an unrecoverable condition for that execution path. With unwinding enabled, stack unwinding runs destructors; an aborting configuration terminates directly. Catching panics is not the normal application error model, and panics must not unwind across an incompatible C ABI boundary.

Libraries often define a precise error enum. Applications often use an error wrapper such as Box<dyn std::error::Error> or a crate like anyhow. Those choices trade explicit error structure against convenient propagation; they do not change what Result means.

8. Traits and generics: capabilities without inheritance

A trait specifies behavior that types can implement:

trait Measure {
    fn measure(&self) -> usize;
}

impl Measure for String {
    fn measure(&self) -> usize {
        self.len()
    }
}

fn twice<T: Measure>(value: &T) -> usize {
    value.measure() * 2
}

T: Measure is a constraint checked at compile time. Generic code is usually monomorphized: the compiler generates specialized code for concrete types. There need not be a virtual call or allocation.

Contrast these signatures:

fn static_size(value: &impl Measure) -> usize { value.measure() }
fn dynamic_size(value: &dyn Measure) -> usize { value.measure() }

The first is essentially a generic parameter with a trait bound; the second uses a trait object, accessed through a data pointer and vtable. Dynamic dispatch does not itself require heap allocation: &dyn Measure borrows, while Box<dyn Measure> owns a heap-allocated value. Not every trait supports trait objects.

In a return position, impl Trait means one concrete implementation type hidden from the caller, not any implementation selected at runtime. Different branches cannot return unrelated concrete types merely because both implement that trait.

Common traits explain much of the standard library:

Trait Meaning
Debug / Display Diagnostic formatting ({:?}) / intended textual formatting ({})
Clone / Copy Explicit duplication / implicit copy semantics
Default A conventional default value
PartialEq, Eq, PartialOrd, Ord Equality and ordering, with differing guarantees
Iterator A source of successive values
From / TryFrom Infallible / fallible conversions
Drop Cleanup when a value is destroyed

Traits can declare associated types. Iterator, for example, has type Item and a next(&mut self) -> Option<Self::Item> method. This associates an element type with an iterator implementation.

Unlike TypeScript interfaces, trait implementations are explicit, not structurally inferred. Coherence rules also generally prevent you from implementing a foreign trait for a foreign type. Wrap it in your own one-field struct—the newtype pattern—when you need local behavior.

9. Strings, slices, collections, and iteration

The everyday vocabulary:

Type Owns storage? Purpose
String Yes Growable UTF-8 text
&str No Borrowed UTF-8 view
Vec<T> Yes Growable contiguous sequence
&[T] / &mut [T] No Shared / exclusive slice
[T; N] Contains elements inline Fixed-length array; length is part of its type
Box<T> Yes Unique ownership of a heap-allocated value
HashMap<K, V> Yes Hash table

Accept &str rather than &String, and &[T] rather than &Vec<T>, unless you need something specific to those owning types. Dereference coercions let callers pass references to the owning types conveniently.

A slice is conceptually a pointer plus a length, not a copy of its elements. A Vec<T> is conceptually pointer, length, and capacity; growing past capacity may relocate its buffer. Neither description is a general license to assume a stable C ABI layout.

Arrays do not implicitly decay into pointers as in C. Ordinary array, slice, and vector indexing is bounds-checked and panics on an invalid index; .get(index) returns Option<&T> instead. Optimizers can eliminate checks they prove unnecessary.

Text is not a byte-indexed array of characters

String::len() counts bytes. Rust rejects text[0] because the intended operation is ambiguous. Use:

  • .bytes() for UTF-8 bytes;
  • .chars() for Unicode scalar values;
  • a Unicode segmentation library for user-perceived characters, or grapheme clusters.

&text[a..b] uses byte offsets and panics unless they are in bounds and on UTF-8 boundaries. .get(a..b) returns an Option<&str> instead. Arbitrary binary data belongs in Vec<u8>; operating-system paths belong in Path/PathBuf, since they need not be valid UTF-8.

Iterators are lazy and usually allocation-free until collected

let values = vec![1, -2, 3];
let squares: Vec<i32> = values
    .iter()
    .copied()
    .filter(|x| *x > 0)
    .map(|x| x * x)
    .collect();

.iter() yields references; .copied() copies Copy elements into values. .collect() allocates the output vector here. Without a consuming operation such as collect, sum, or a for loop, the pipeline does no traversal.

.into_iter() invokes consuming iteration for its receiver: on an owned vector it moves out elements; on a reference it borrows. This distinction matters far more than the method's name alone.

Closures use |argument| expression and infer their capture modes from their bodies. move || ... captures by value—moving non-Copy captures—rather than borrowing the surrounding bindings. That does not automatically make a closure callable only once; what its body does determines that.

10. Shared ownership, threads, and async

If one owner is not the right model, choose sharing explicitly:

  • Rc<T>: reference-counted ownership within one thread.
  • Arc<T>: atomic reference-counted ownership suitable for sharing across threads when T meets the required thread-safety bounds.
  • RefCell<T>: interior mutability with borrowing rules checked at runtime; conflicting borrows panic, or return errors through try_borrow methods.
  • Mutex<T> / RwLock<T>: synchronized interior access, suitable for cross-thread use with appropriate T.

Rc<RefCell<T>> and Arc<Mutex<T>> are common combinations. Neither should be your reflexive translation of every Python object. They add runtime work and can obscure a simpler ownership design. Strong reference cycles can leak; Weak<T> provides non-owning links.

Two traits encode important concurrency properties:

  • Send: ownership can safely transfer to another thread.
  • Sync: shared references can safely be shared between threads.

These are usually derived automatically from a type's components. Arc<T> does not make an otherwise unsafe-to-share T magically thread-safe. Ordinary detached-capable thread::spawn closures need 'static captures; scoped threads can instead borrow surrounding data.

Data-race freedom does not imply race-free application logic: lock ordering, atomic protocols, and distributed state remain your responsibility.

async fn produces a future; calling it does not immediately execute its body. Futures must be polled, normally by an executor. .await can suspend the current task instead of blocking its operating-system thread. The standard library defines the core abstractions, but commonly used runtimes such as Tokio are separate dependencies.

Async is not automatic parallelism. Blocking I/O still blocks a runtime worker unless handled appropriately. Holding a synchronous lock guard across .await can prevent scheduling progress or make a future unsuitable for spawning. Learn ownership first; async combines those same rules with suspended execution.

11. A complete small program

Replace src/main.rs in the Cargo project with this. It reads a UTF-8 file containing one integer per nonblank line and prints their sum:

use std::{env, error::Error, fs, io, process::ExitCode};

fn run() -> Result<(), Box<dyn Error>> {
    let path = env::args_os().nth(1).ok_or_else(|| {
        io::Error::new(io::ErrorKind::InvalidInput, "usage: rust-tour FILE")
    })?;
    let input = fs::read_to_string(path)?;
    let mut total = 0_i64;

    for (index, line) in input.lines().enumerate() {
        let line = line.trim();
        if line.is_empty() {
            continue;
        }
        let value = line.parse::<i64>().map_err(|error| {
            io::Error::new(
                io::ErrorKind::InvalidData,
                format!("line {}: {error}", index + 1),
            )
        })?;
        total = total.checked_add(value).ok_or_else(|| {
            io::Error::new(io::ErrorKind::InvalidData, "sum exceeds i64 range")
        })?;
    }
    println!("{total}");
    Ok(())
}

fn main() -> ExitCode {
    match run() {
        Ok(()) => ExitCode::SUCCESS,
        Err(error) => {
            eprintln!("error: {error}");
            ExitCode::FAILURE
        }
    }
}

Notice how the pieces cooperate: input owns the text; lines() and trim() borrow slices from it; parsing produces owned numbers; ? propagates errors; closures construct contextual errors only when needed. No string cloning or explicit deallocation is required. The whole file is loaded into memory—streaming would be a separate design choice.

checked_add makes overflow behavior intentional. Ordinary integer overflow is checked and panics in Cargo's default debug profile; the default release profile disables those checks and wraps. Use checked, saturating, or wrapping methods when that behavior is part of your algorithm rather than relying on build settings.

Tests commonly live alongside the code, in a module compiled only for testing:

#[cfg(test)]
mod tests {
    #[test]
    fn parses_a_signed_integer() {
        assert_eq!(" -5 ".trim().parse::<i64>(), Ok(-5));
    }
}

cargo test discovers #[test] functions; a panic fails the test. Larger integration tests go under tests/ and use your library's public API.

12. The C escape hatch—and the boundaries to remember

unsafe permits specific operations that safe Rust cannot verify, such as dereferencing raw pointers or calling unsafe functions. It is not a switch that disables type checking or the borrow checker for an entire block.

The author of unsafe code must establish its safety invariants. Safe callers of a correctly designed wrapper should not have to do so. Rust's standard collections use unsafe internals to expose safe interfaces; the right goal is a small, audited boundary, not zero unsafe code anywhere in the dependency graph.

For C interoperability, use an appropriate extern "C" interface, C-compatible field types and representations such as #[repr(C)] structs, and an explicit ownership contract. Rust's ordinary String, references, and default-layout structs are not a portable C API. Raw pointers can be null or dangling; turning one into a reference requires satisfying the reference's validity and aliasing rules. Allocations must be released through a compatible allocator and ownership protocol.

One last distinction: Rust references are not merely “C pointers with syntax sugar.” Their stronger guarantees are exactly what make safe code safe—and what unsafe code must never violate.

Where to go next

Use this decision checklist while writing your first program:

  1. Need to retain the value? Own it: String, Vec<T>, or your own struct.
  2. Only need to inspect it? Borrow it: &T, &str, &[T].
  3. Need to modify it temporarily? Borrow exclusively: &mut T.
  4. Can it be absent or fail? Model that with Option or Result.
  5. Need multiple owners? Decide whether reference counting is truly necessary, and whether the sharing crosses threads.

Then build a small CLI with a parser and tests. Resist cloning merely to silence the compiler until you understand which ownership relationship caused the error; once understood, a deliberate clone can be the best engineering choice.

For deeper study:

  • The Rust Programming Language: the main tutorial, especially ownership, lifetimes, and error handling.
  • Rust by Example: runnable, focused examples.
  • Standard library documentation: read method signatures; they describe ownership and failure behavior unusually well.
  • The Edition Guide: what editions change, and what they do not.

The main idea: Rust does not ask you to forget C's memory model. It asks you to state—and let the compiler check—the ownership and access discipline you previously had to maintain yourself.

Rust, for people who already know C

For working programmers. Assumes you can read a pointer, a dict, and a discriminated union without help. Everything below is stable Rust as of late 2026 (rustc 1.99, edition 2024).

Rust is C's machine model with a type system that tracks who owns what. Same stack frames, same heap, same cache behaviour, same malloc underneath. The difference is that pointers carry a compile-time proof of validity, and the proof is checked before your program ever runs.

That's the whole trick. Everything else — traits, Result, async — is ordinary language design that happens to fit around it.

If you already write C, you will find that Rust is mostly familiar things made checkable: &mut T is restrict that the compiler enforces, Drop is goto cleanup that cannot be forgotten, match is a switch that must cover every case, Result is errno as a return value, and slices are arrays that remember their length. The unfamiliar part is that these guarantees are threaded through the type system, so two thirds of the work moves from runtime debugging to compile errors.

The five ideas

  1. Values have one owner. When it goes out of scope, the value is freed, deterministically, by calling its destructor (Drop). No GC, no refcounting by default.
  2. You can borrow instead of moving. &T is a shared borrow, &mut T is an exclusive one. Many shared or one exclusive, never both. The compiler uses this to prove pointers stay valid.
  3. Enums are tagged unions, and match is exhaustive. Option<T> replaces null, Result<T, E> replaces errno and exceptions.
  4. Traits are nominal interfaces, checked at compile time, dispatched either statically (monomorphised generics, like C++ templates but type-checked) or dynamically (a fat pointer with a vtable, like the hand-rolled struct-of-function-pointers you've written in C).
  5. unsafe is an explicit, local escape hatch for raw pointers and FFI — not a mode you turn on for the whole program.

There is no inheritance, no implicit conversions, no null, no exceptions, no overloaded =, and — in safe code — no runtime type errors. The language is smaller than C++ and stricter than C.

First program, and what's hiding in it

use std::collections::HashMap;

fn main() {
    let text = "the quick brown fox jumps over the lazy dog the end";
    let mut counts: HashMap<&str, u32> = HashMap::new();

    for word in text.split_whitespace() {
        *counts.entry(word).or_insert(0) += 1;
    }

    let mut pairs: Vec<_> = counts.into_iter().collect();
    pairs.sort_by_key(|&(_, n)| std::cmp::Reverse(n));

    for (word, n) in pairs.iter().take(3) {
        println!("{word:>8} {n:>3}");
    }
}

Line by line, for a C reader:

  • let declares; mut opts into mutation. Bindings are immutable by default — the opposite default from C, and it eliminates a class of "who changed this?" bugs.
  • "..." is a &'static str pointing into the binary's rodata. No allocation.
  • HashMap<&str, u32> borrows its keys from text; nothing is copied. Python's Counter is this in one line, but here you can see who owns the memory.
  • entry(word).or_insert(0) is the C idiom if (!(p = find(k))) { p = insert(k, 0); } *p += 1; expressed so that the "insert if missing" path can't be forgotten.
  • Vec<_> — the _ means "infer this"; collect() is generic over its target container, and the annotation picks Vec<(&str, u32)> for you.
  • sort_by_key takes a closure — a function pointer plus captured environment. C's qsort needs a void* and a comparator; here the compiler generates a specialised comparator and inlines it.
  • dbg!(x) prints the expression, its value, file and line, then hands the value back, so it drops into the middle of an expression. Closest thing to a printf you can leave in.
  • println! is a macro, not a function: it checks the format string at compile time. {word:>8} pulls in a local variable, with alignment; {:?} prints any #[derive(Debug)] type.

The syntax details that trip up C programmers: a block is an expression (let x = if c { 1 } else { 2 }; is legal), semicolons matter ({ 1 } yields 1, { 1; } yields ()), and if conditions must be bool — no if (ptr). That last rule alone kills a whole family of bugs.

Ownership

Every value has exactly one owner. Assignment moves; leaving scope drops.

let s = String::from("hello");   // s owns a heap buffer
let t = s;                       // ownership moves to t
println!("{s}");                 // error[E0382]: borrow of moved value: `s`

error[E0382]: borrow of moved value: `s`
  |
2 |     let s = String::from("hello");
  |         - move occurs because `s` has type `String`,
  |           which does not implement the `Copy` trait
3 |     let t = s;
  |             - value moved here
4 |     println!("{s}");
  |                ^ value borrowed here after move

Physically this is a 24-byte header copy; semantically the source is dead. At -O the copy usually disappears. Types that are "plain old bits" — integers, floats, bool, char, arrays of them, and structs you mark #[derive(Clone, Copy)] — are Copy, so they behave exactly like C values and can be used after assignment. Everything owning a resource (String, Vec, Box, File, sockets) is move-only. This is the same distinction C++ makes with copy constructors, but derived automatically from whether the type has a destructor.

Three consequences worth internalising:

  • Destruction is deterministic and ordered. Values drop in reverse declaration order at the end of the enclosing block, including on early return and on panic. That is goto cleanup for free, and it is why Rust code has no goto out: ladder.
  • Passing by value can be cheap or expensive, and the type tells you which. fn f(v: Vec<u8>) takes ownership and does not copy the buffer. fn f(v: &[u8]) borrows. There is no hidden deep copy, ever, unless you call .clone().
  • The compiler elides most moves. Returning a Vec from a function is not a copy; it is the same buffer, moved through registers (and often constructed in place).

When you need two references to the same value, you either borrow temporarily or reach for shared ownership (Rc/Arc, below). When you need an optional value, you use Option<T> — and because Box<T>, &T, Vec<T> and String all have a non-null niche, Option<Box<T>> and Option<&T> are still 8 bytes. No null pointer, no size cost.

Borrowing, and what the checker is actually doing

fn total(xs: &[f64]) -> f64 { xs.iter().sum() }

fn main() {
    let mut v = vec![1, 2, 3];
    let first = &v[0];
    v.push(4);            // error[E0502]: cannot borrow `v` as mutable ...
    println!("{first}");
}

The rule is many readers XOR one writer. It is the rule you already follow informally in C — you don't realloc a buffer while holding a pointer into it — except the compiler enforces it and the error appears at the exact line where the aliasing starts.

The checker is a liveness/dataflow analysis over the control-flow graph, not a scope-based rule and definitely not a runtime mechanism. A borrow ends at its last use (non-lexical lifetimes), so this is fine:

let mut v = vec![1, 2, 3];
let first = &v[0];
println!("{first}");
v.push(4);                 // ok: the borrow is already dead

Lifetimes are the names for those inferred regions. You only write them when inference is ambiguous — typically in structs that hold references, or functions with several reference parameters and a reference return:

struct Parser<'a> { input: &'a str, pos: usize }

fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

'a compiles to nothing. It is a proof obligation, not a runtime object, which is why "lifetimes are hard" is really "the compiler is asking you to specify an invariant you were previously keeping in your head". Most application code writes zero lifetimes; &str in, String out, and the elision rules do the rest. In structs, holding owned data (String, Vec) rather than references removes the parameters entirely — the standard advice is: start owned, borrow at the edges.

&mut T deserves a note: it is a unique pointer, so the compiler can hand LLVM noalias metadata for it exactly as C's restrict promises. This is one reason Rust often matches or beats tuned C on loop-heavy code: aliasing information is guaranteed rather than promised by convention.

Three idioms that resolve most borrow-checker friction:

let mut v = vec![1, 2, 3, 4];
let (left, right) = v.split_at_mut(2);   // two disjoint &mut into one Vec
for x in &mut v { *x *= 2; }              // exclusive borrow, one element at a time
v.retain(|x| *x > 0);                     // mutate/remove without holding indices

And the structural fix: if you need to mutate a graph or tree while traversing it, don't hold &mut across the traversal. Store nodes in a Vec and link them by u32 index. It is exactly the layout you'd choose in C for cache reasons, and it sidesteps the borrow checker for the same reason.

Slices, strings, and what a reference physically is

A Rust reference is one or two machine words and no metadata beyond that:

  • &T / &mut T / Box<T> — one pointer.
  • &[T] / &str — pointer plus length (a fat pointer), 16 bytes.
  • &dyn Trait — pointer plus vtable pointer, 16 bytes.
  • Vec<T> / String — pointer, length, capacity, 24 bytes.

The middle two are the important ones. A slice is your (T*, size_t) pair promoted to a first-class value with bounds checks on indexing and no separate length argument to get wrong. &Vec<T> coerces to &[T]; write your functions to take &[T] and they'll accept arrays, vectors, and sub-slices.

Strings are UTF-8, not NUL-terminated, and not indexable by integer:

let s = "héllo";            // 6 bytes, 5 chars
assert_eq!(s.len(), 6);     // bytes
assert_eq!(s.chars().count(), 5);
// s[1] would panic: byte 1 is not a char boundary
for c in s.chars() { /* ... */ }

String is the growable owned type; &str is the borrowed view. The convention that makes APIs pleasant: take &str, return String. For C interop you convert explicitly — CString adds the NUL, CStr borrows one, and both check for interior NULs. For filesystem paths use Path/PathBuf rather than strings; on Unix a path is bytes, not UTF-8, and Rust models that correctly.

Enums, Option, Result, and match

#[derive(Debug, Clone, Copy)]
enum Shape {
    Circle { r: f64 },
    Rect { w: f64, h: f64 },
}

impl Shape {
    fn area(&self) -> f64 {
        match *self {
            Shape::Circle { r } => std::f64::consts::PI * r * r,
            Shape::Rect { w, h } => w * h,
        }
    }
}

An enum is a tagged union whose discriminant is sized by the compiler, with no invalid states representable. match destructures it and must be exhaustive — adding a variant breaks every non-wildcard match at compile time, which is the closest thing to a free refactor you'll get in a statically typed language. Guards, ranges, and nesting all work:

match (code, retries) {
    (200, _) => Ok(body),
    (500..=599, n) if n < 3 => retry(),
    (401 | 403, _) => Err(Auth),
    (c, _) => Err(Unexpected(c)),
}

Option<T> and Result<T, E> are ordinary enums in std, not compiler magic. There are no exceptions and no errno; a function that can fail says so in its type, and ? propagates:

fn port(s: Option<&str>) -> Result<u16, ConfigError> {
    let raw = s.ok_or(ConfigError::Missing("port"))?;  // Option -> Result
    Ok(raw.parse()?)     // ParseIntError -> ConfigError, via impl From<_>
}

? is early-return plus From::from on the error, so ? also performs error-type conversion — which is why that snippet needs impl From<ParseIntError> for ConfigError somewhere, and why libraries define one error enum per module and let ? do the plumbing. In application code, anyhow::Result<T> boxes any error; in library code, thiserror generates the enum and the From impls from #[from]. Box<dyn Error> is the lowest-common-denominator type when you don't care. Binary entry points can return Result too, so fn main() -> anyhow::Result<()> and a bare ? is the standard shape for a CLI.

Two things C programmers ask immediately:

  • unwrap() is not "ignore the error". It panics — abort the thread, run destructors, print a message. Use it for bugs and prototypes, expect("...") when the message should say what invariant broke. In a server, a panic in one task doesn't take down the process by default.
  • Panics are not exceptions. They are for broken invariants, not control flow. They unwind by default (panic = "abort" in your profile turns that off, which also makes binaries smaller), and they cross an FFI boundary only over extern "C-unwind".

if let, let ... else, and (edition 2024) let chains keep this readable:

if let Some(user) = lookup(id) && user.active && let Ok(n) = user.age.parse::<u8>() {
    println!("{n}");
}

let Some(cfg) = load() else { return Err(ConfigError::Missing("config")) };

Traits, generics, and the two kinds of dispatch

A trait is a set of methods a type can implement. It is nominal: the impl is written explicitly, unlike TypeScript's structural types or Go's interfaces, which means the set of behaviours a type has is a closed, searchable list — and the compiler can warn about a missing one.

trait Area {
    fn area(&self) -> f64;

    fn describe(&self) -> String {              // default method
        format!("{:.2} square units", self.area())
    }
}

impl Area for Shape { fn area(&self) -> f64 { /* as above */ } }

Generic functions are monomorphised: one copy of the machine code per concrete type, so calls inline and the abstraction costs nothing:

fn total<T: Area>(items: &[T]) -> f64 {
    items.iter().map(|x| x.area()).sum()
}

total(&vec![Shape::Circle { r: 1.0 }]);   // total::<Shape>, fully inlined

dyn Trait is the other choice: one copy of the function, a vtable lookup per call, and the ability to hold heterogeneous values:

fn total_dyn(items: &[Box<dyn Area>]) -> f64 {
    items.iter().map(|x| x.area()).sum()
}

let shapes: Vec<Box<dyn Area>> = vec![
    Box::new(Shape::Circle { r: 1.0 }),
    Box::new(Shape::Rect { w: 2.0, h: 3.0 }),
];

A realistic signature, decoded:

fn load(path: impl AsRef<Path>) -> Result<Config, ConfigError>

impl AsRef<Path> is an anonymous generic — "anything that can be viewed as a path" (&str, String, PathBuf), monomorphised per caller. Result<Config, ConfigError> says it can fail and with what. That's most of what Rust signatures ever say: one constraint per argument, one honest return type. There are no hidden exceptions and no hidden allocation.

Rules of thumb: generics for library internals and hot paths, dyn at boundaries, when you need runtime extensibility (plugins, test doubles), or when monomorphisation would blow up compile time and binary size. impl Trait in argument position is sugar for a generic; in return position it means "a concrete type I'm not naming" (an opaque type), which is how async fn works under the hood.

The trait machinery you'll actually use daily:

Trait Means Derivable?
Debug {:?} formatting yes
Clone / Copy explicit deep copy / implicit bit copy yes
PartialEq, Eq, Hash, Ord comparison, hashing, sorting yes
Default zero-ish value yes
Display {} formatting no, write it
From / Into, TryFrom infallible / fallible conversions no
Iterator for loop protocol, adapters no, implement next

Two constraints surprise people. Coherence/orphan rule: you can implement a trait for a type only if the trait or the type is local to your crate. That prevents two dependencies from adding conflicting impls, and it's why you see the newtype pattern (struct Meters(f64);) to attach foreign traits to foreign types. No inheritance: share behaviour by composing and by using supertraits (trait Shape: Area + Debug), not by subclassing. There is no virtual, no override, no fragile base class problem.

If you're coming from TypeScript: think of traits as interfaces that are checked, not erased. There is no any, no as escape from the type system, and no runtime shape checks — a "compile-time-only" abstraction is genuinely free, and a wrong assumption is a compile error, not a undefined at 3 a.m.

Memory management in practice

You will not call malloc or free. You will choose a container, and the container's Drop does the rest:

You want Use Cost model
One heap value Box<T> malloc/free
Growable array Vec<T> amortised doubling, like a C dynamic array
Owned text String same, UTF-8 validated on insert
Shared, read-only Rc<T> / Arc<T> refcount; Arc is atomic
Shared, mutable Rc<RefCell<T>> / Arc<Mutex<T>> runtime borrow check (panics) / lock
Optional global OnceLock<T> / LazyLock<T> once-init, then a load
Maybe-owned string Cow<'a, str> borrow until you must allocate

RefCell<T> is worth understanding: it moves the borrow rules to runtime. borrow() and borrow_mut() return guards, and violating the aliasing rule panics instead of failing to compile. It's the right tool for caches, observer lists, and graphs — and, like Rc, it is single-threaded, which the compiler enforces because Rc<T> is not Send.

For tree/graph-shaped data, the idiom that scales is arenas plus indices (Vec<Node>, u32 links), or a crate like bumpalo or typed-arena. That is exactly the C approach — contiguous storage, integer handles — with the added benefit that the borrow checker stops complaining because there are no long-lived pointers.

Drop is the destructor trait. It runs on scope exit, on ?, on break, and on unwind. You implement it for resource handles (file descriptors, locks, GPU buffers) to get RAII; you almost never implement it for plain data. std::mem::forget and ManuallyDrop let you leak deliberately; the one way Rc leaks by accident is a reference cycle. Allocators are pluggable per binary via #[global_allocator] — jemalloc, mimalloc, and a custom arena all work.

Concurrency

The ownership rules generalise to threads with two marker traits:

  • Send — the value can move to another thread.
  • Sync — &T can be shared across threads.

They are auto-derived structurally, and !Send types (Rc, RefCell, raw pointers) are rejected at the spawn call. Data races are therefore a compile error, not a code review item. Locks and channels are ordinary library types:

use std::sync::{Arc, Mutex};

let counter = Arc::new(Mutex::new(0u64));
let mut handles = Vec::new();
for _ in 0..8 {
    let c = Arc::clone(&counter);
    handles.push(std::thread::spawn(move || {
        for _ in 0..1000 { *c.lock().unwrap() += 1; }
    }));
}
for h in handles { h.join().unwrap(); }

If you don't need 'static threads, std::thread::scope lets spawned threads borrow from the stack — no Arc required. For data parallelism, rayon turns iter() into par_iter() and gives you work-stealing without changing the algorithm. Message passing is std::sync::mpsc (or crossbeam / flume for more features). Atomics are std::sync::atomic, with explicit Ordering.

Async is the part where Rust is still visibly a work in progress. An async fn compiles to a function returning a state machine implementing Future; nothing runs until an executor polls it. The standard library defines the trait but ships no runtime, so you pick one — tokio for I/O, smol for a smaller stack, embassy for embedded. Consequences:

  • #[tokio::main] is a macro that builds a runtime and blocks on your future.
  • Futures are lazy; let f = fetch(); does nothing until .await.
  • tokio::spawn requires Send + 'static; borrow across tasks needs scoped tasks or Arc.
  • A blocking call inside a task stalls a worker thread; use spawn_blocking.
  • Pin exists because the generated state machines are self-referential. You meet it in signatures, rarely in code.

Async closures are stable (1.85) and async fn in traits has been stable since 1.75, but async methods are not yet usable through dyn Trait — that's a 2026–2027 goal, along with async drop and scoped spawning. In practice: use async for I/O-bound servers, threads for CPU-bound work, and rayon for data parallelism. Don't mix them casually. If you need both, tokio::task::spawn_blocking is the seam.

unsafe, FFI, and talking to C

unsafe unlocks five things: dereferencing raw pointers, calling unsafe functions, accessing static mut, implementing unsafe traits, and reading union fields. It does not disable the borrow checker, and it does not mean "trust me" — it means "I have checked these specific preconditions", which you should write down:

/// # Safety
/// `p` must be valid for reads of `len` bytes and not aliased for the duration.
unsafe fn checksum(p: *const u8, len: usize) -> u32 {
    let mut sum = 0u32;
    for i in 0..len {
        // SAFETY: caller guarantees p is valid for len bytes.
        sum = sum.wrapping_add(unsafe { *p.add(i) } as u32);
    }
    sum
}

The C boundary is designed to be boring:

#[repr(C)]
pub struct Point { pub x: f64, pub y: f64 }

#[unsafe(no_mangle)]                       // edition 2024 spelling
pub extern "C" fn distance(a: Point, b: Point) -> f64 {
    ((a.x - b.x).powi(2) + (a.y - b.y).powi(2)).sqrt()
}

unsafe extern "C" { fn abs(i: i32) -> i32; }

#[repr(C)] fixes the layout, extern "C" fixes the calling convention, #[unsafe(no_mangle)] fixes the symbol name. From there: bindgen generates Rust bindings from C headers; cbindgen generates a C header from Rust; cxx does the C++ equivalent. cargo build --crate-type=cdylib (or staticlib) produces a .so/.a you can link from a C build system.

Worth knowing: since Rust 1.99 you can define C-variadic functions natively (unsafe extern "C" fn f(n: u32, args: ...) with VaList::next_arg), which used to require a shim. And no_std lets you drop the standard library for kernels and microcontrollers, keeping core (no allocator) or alloc.

Two structural facts about the ecosystem: Rust has no stable ABI, so crates are distributed as source and compiled together (that's why generics and #[inline] can be so aggressive); and the stable interface between Rust and everything else is the C ABI. Plan your FFI boundary around plain #[repr(C)] structs and extern "C" functions, not around Rust types.

Your existing debugging tools still work: gdb/lldb understand Rust symbols, perf and cargo flamegraph profile it, rr records it, and RUST_BACKTRACE=1 turns a panic into a stack trace. What changes is how rarely you need them — most of what you'd run valgrind to find (use-after-free, uninitialised reads, buffer overruns) is a compile error here.

Tooling worth installing on day one: cargo-nextest (faster, better test output), cargo-expand (see what macros generated), cargo-tree, cargo-audit or cargo-deny (supply chain — the ecosystem has had real attacks), and miri (an interpreter that finds undefined behaviour in unsafe code, including out-of-bounds and aliasing violations). Link with lld or mold if link times annoy you; lld has been the default on Linux x86-64 since 1.90. Rust links its own dependencies statically and libc dynamically by default; target x86_64-unknown-linux-musl if you want a single fully static binary, which is common for container images.

What will annoy you

Honest list, because the marketing isn't.

Compile times. A clean build of a mid-sized dependency tree is minutes, and monomorphisation makes it worse. cargo check and incremental builds mitigate it; nothing makes it as fast as Go. Template-heavy Rust is the slowest.

Borrow-checker friction, at first. You will write code that is obviously correct and be told it isn't, because the checker reasons per-path and per-alias, not per-intention. The fix is almost never "add clone()" (though that's the fast fix); it's restructuring — pass slices, split borrows, use indices, shorten the borrow's live range. After a few weeks the errors become predictable, and you start designing data structures the checker likes.

Pin, Send bounds, and async diagnostics. The error messages in async code are the worst in the language: a missing Send surfaces as a wall of "future is not Send" with the real cause several layers down. cargo expand shows you the generated state machine; patience helps more.

Verbose conversions. u8 to usize is as, but i64 to u32 is try_into()?, and as silently truncates — the exact bug C has. Rust makes the safe path easy to write, not invisible. And integer overflow panics in debug builds but wraps in release, so a test that passes with cargo test can still be wrong in production.

Dyn-compatibility rules. Not every trait can become dyn Trait (no generic methods, no Self-returning functions). The compiler tells you precisely why, but it's a concept you have to learn.

Ecosystem gaps. GUI, scientific computing, and some FFI-heavy domains are less mature than C++ or Python. Async has visible seams. unsafe crates vary in quality; read the SAFETY comments.

No stable ABI. Distributing a Rust library to non-Rust consumers means C ABI, which means manual marshalling. Plugin systems are still awkward.

The type system can't express everything. Self-referential structs, doubly-linked lists, and mutable graphs need arenas, indices, or unsafe. This is not a bug — those structures are hard in C too — but Rust makes you say so.

And the other side of the ledger, which is why people stay: no use-after-free, no double-free, no data races, no null dereferences, no iterator invalidation, no forgotten free on the error path, no "works on my machine because of an uninitialised variable", and a compiler that turns "did I handle this case?" into a build failure.

How to actually learn it

Read The Rust Programming Language (the Book) — chapters 4 (ownership), 6 (enums), 10 (generics, traits, lifetimes) and 13 (iterators/closures) carry most of the weight. Then do Rustlings, which is ~90 small exercises with instant compiler feedback; it is the fastest way to convert C intuitions into Rust ones. Keep the standard library docs open — they are unusually good, and every page has examples that run.

Then build something real, with dependencies: a CLI with clap, reading JSON with serde, errors with anyhow, and a .await somewhere. Port a small C utility and notice where the code gets shorter (resource handling, parsing, string manipulation) and where it gets longer (borrowing across data structures, generic bounds).

Three habits that pay off:

  1. Write cargo check-driven. Let the compiler drive; fix the first error, not all of them.
  2. Clone first, optimise later. clone() is a correctness-preserving escape hatch. Measure before removing it — often the profiler says it doesn't matter.
  3. Learn to read rustc --explain E0xxx. The error index is a tutorial keyed to your exact mistake, and the compiler's suggested fixes are usually right.

Rust's real cost is a few weeks of unlearning: you stop thinking "who frees this?" and start thinking "who owns this, and for how long?" Once that question is automatic, the language gets out of the way — and the class of bugs you used to debug at 2 a.m. simply stops existing.

Rust for People Who Already Know C, Python, and TypeScript

An 18-minute introduction. Nothing here assumes C++; several ideas will look familiar from it anyway, and those are flagged when they appear.

You already have three useful mental models:

  • C: values have a size and an address, memory is yours to mismanage, and the compiler mostly trusts you.
  • Python: objects live on the heap behind references, a garbage collector cleans up, and almost anything can fail at runtime with an exception.
  • TypeScript: a rich static type system — generics, unions, narrowing — that is erased before execution and therefore promises nothing at runtime.

Rust is best understood as an attempt to keep C's model — explicit layout, stack allocation, no garbage collector, compile to native code — while making the compiler prove the things C leaves to discipline, and to give that proof a type system closer in spirit to TypeScript's than to C's. The price is that the compiler will reject programs you know are "probably fine", and you will spend your first weeks arguing with it. This document is about what it is proving, why, and how to stop arguing.

One sentence version: every value has exactly one owner; you may lend it out under strict rules; the compiler verifies statically that no loan outlives the value or overlaps a writer. Almost everything distinctive about Rust follows from that.

Two clarifications. First, "no runtime" means no GC, no interpreter, no object header, no hidden allocation: a Rust binary has a small runtime in the C sense (stack setup, panic machinery) but nothing that inspects your heap. It can run with no OS (no_std: kernels, firmware, bootloaders) and its binaries look, to a debugger, much like C binaries. Second, "safe" has a precise meaning: in code not marked unsafe, Rust guarantees no use-after-free, no double-free, no null or uninitialised dereference, no data races, and no out-of-bounds access (bounds checks are runtime, and panic rather than corrupt memory). Logic bugs, deadlocks, memory leaks, and panics remain entirely possible.

The toolchain is unusually unified, which will feel luxurious coming from C and familiar-but-better coming from Python/TS:

$ curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh   # or your package manager
$ cargo new hello && cd hello
$ cargo run        # build + run        $ cargo test     # run #[test] functions
$ cargo clippy     # a very opinionated linter   $ cargo fmt   # the one true formatter

cargo is simultaneously make, pip/npm, a test runner, a doc generator (cargo doc produces genuinely good HTML from doc-comments), and a dependency solver with a lockfile. Libraries ("crates") come from crates.io, are compiled from source into your binary, and are versioned with semver that cargo actually enforces. There are no header files and no include paths: a crate is a module tree, pub marks what's exported, and use std::collections::HashMap; is an import, not a textual inclusion.

Editions are Rust's answer to evolving without breaking the world: 2015, 2018, 2021, 2024. An edition is chosen per-crate in Cargo.toml, the compiler supports all of them forever, and crates of different editions link together freely. Examples here use edition 2024. Rust releases every six weeks and "stable" is a hard promise: code that compiles today compiles in ten years, minus rare, loudly-announced soundness fixes.

2. The core: ownership

Forget garbage collection and forget malloc/free pairing. In Rust, each value has one owner — a variable, a struct field, a slot in a vector. When the owner goes out of scope, the value is dropped: its destructor runs and its resources (heap memory, file handles, sockets, locks) are released, deterministically, exactly there. If you know C++'s RAII, it is that, but applied to every type with no opt-out, so it needs no prior C++ knowledge to use: scope exit = cleanup, as if the compiler inserted the right free/fclose/close for you, in reverse order of construction.

Assignment and argument-passing move non-trivial values instead of copying them:

let s1 = String::from("hello");   // s1 owns a heap buffer
let s2 = s1;                      // ownership MOVES to s2; the buffer is not copied
println!("{s1}");                 // ✗ compile error: use of moved value

This is the single biggest surprise for a C programmer: s2 = s1 looks like a struct copy (and in C it would be a shallow memcpy — the classic double-free setup), but in Rust it is a transfer after which the source is statically dead. For a Python/TS programmer: assignment does not create a second reference to a shared object; it hands the object over. If you genuinely want a copy, say so: s1.clone() performs the deep copy, visibly, at a cost you can see in the code. Small plain-data types — integers, floats, bool, char, and tuples/arrays of them — are marked Copy and do copy silently, exactly as in C, because copying them is free and they own nothing.

Functions participate in the same system. Passing a String by value gives it away; taking &String borrows it; returning a value moves ownership to the caller. There is no third, implicit mode.

Borrowing

A reference is a borrow: access without ownership, and without the right to free anything.

  • &T — a shared reference. Read-only, and any number may exist simultaneously. Think const T*, except the compiler proves the pointee outlives the pointer.
  • &mut T — an exclusive reference. Read-write, and while it exists, no other reference to that value may be used. Think T*, plus a uniqueness guarantee no C compiler gives you.

The rule is often stated as aliasing XOR mutation: data is either shared or mutable, never both, at any instant. This is not an optimisation hint (though LLVM exploits it heavily, which is part of why Rust is fast). It is what kills whole bug classes:

  • Use-after-free / dangling pointers — a reference cannot outlive its owner (§3).
  • Iterator invalidation — v.push(x) needs &mut v; if you hold &v[0] across it, that's a shared borrow overlapping a mutable one: compile error. The segfault you have debugged in C, and the RuntimeError: dictionary changed size you have caught in Python, become a build failure with a helpful message.
  • Data races — two threads can only race if one can mutate while another accesses; the XOR rule, extended across threads (§7), forbids exactly that.

Mutation being a type-level property is worth pausing on. C's const is shallow and castable; TS's readonly is shallow and erasable. In Rust, &T vs &mut T is as fundamental a distinction as i32 vs String, it is transitive (a & to a struct gives you &s to its fields, never &mut), and there is no const_cast. Separately, bindings are immutable by default: let x = 5; cannot be reassigned unless you write let mut x = 5;. Immutability-by-default plus move semantics will feel familiar from functional programming; it is there to make the borrow checker's job — and the reader's — tractable.

When shared mutation is genuinely the design (a cache behind a read API, a graph), Rust offers interior mutability: Cell, RefCell, Mutex, RwLock. These move the XOR check to runtime — RefCell will panic if you break the rule dynamically, much like a Python error — and their presence in a type is visible in its signature. They are the marked escape valves, not the norm.

Lifetimes: the part everyone fears, mostly unnecessarily

If references can never outlive their owner, someone must check "never outlives". That check is lifetime analysis, and the scary-looking 'a annotations are simply names for the regions being compared — in function signatures, where the compiler cannot infer them. You write them rarely, because of elision: in the common cases (one input reference, or &self) the output clearly borrows from one source and the compiler fills it in.

Read this signature the way you'd read a contract:

fn longest<'a>(x: &'a str, y: &'a str) -> &'a str

"Given two string views that both live at least as long as some region 'a, I return a view that lives no longer than 'a." That is all a lifetime ever says. Lifetimes are erased at compile time: they cost nothing, allocate nothing, and appear nowhere in the binary. The C translation is "this returns a pointer into one of its arguments, not into a local or a fresh allocation" — a fact C forces you to document in a comment and Rust forces the caller and callee to agree on, mechanically. Returning a pointer to a local, the C bug, is rejected: the local's region ends at the closing brace and the return type demands a longer one.

3. The language, at speed

You can skim this section; everything is chosen for contrast with what you know.

Syntax and basics. C-flavoured braces and semicolons, but statements are expressions: if, match, and bare blocks return values, and a function's return value is its last expression without return (early return still exists). Type inference is strong but local: let v = vec![1, 2, 3]; needs no annotation, but function signatures are fully annotated — inference never crosses a function boundary, which keeps APIs honest and error messages local. There is a fixed menu of integer types (i8…i128, u8…u128, isize/usize, f32/f64) and no implicit numeric conversions at all: i32 + i64 is an error, as casts are explicit, and integer overflow panics in debug builds and wraps (with explicit wrapping_add etc. when that's what you mean) in release. char is a 4-byte Unicode scalar value, not a byte. Variables may be shadowed (let x = x.trim();), which is idiomatic for transformation pipelines.

Structs, enums, and pattern matching. Structs are plain data with named or tuple fields; methods live in separate impl blocks; there is no inheritance, at all, ever (§4). Enums are algebraic data types — TS discriminated unions, but native and exhaustively checked:

enum IpAddr {
    V4(u8, u8, u8, u8),
    V6(String),
}

let home = IpAddr::V4(127, 0, 0, 1);
match home {
    IpAddr::V4(127, _, _, _) => println!("loopback"),
    IpAddr::V4(a, b, c, d)   => println!("{a}.{b}.{c}.{d}"),
    IpAddr::V6(s)            => println!("[{s}]"),
}

match must cover every case (the compiler lists the ones you missed), binds the payload while checking the variant — no TS-style "narrowing was lost inside the closure" — and is an expression. The two enums you will use hourly are in the standard library and replace two of your languages' warts:

  • Option<T> — Some(x) or None. There is no null in Rust. A function that might not find something returns Option; the type system forces you to handle None before touching the value. No NullPointerException, no Cannot read properties of undefined, no segfault, unless you explicitly .unwrap() and accept a panic as your handling.
  • Result<T, E> — Ok(x) or Err(e), for anything fallible. See §5.

Strings will hurt briefly, then make sense. Rust strings are guaranteed UTF-8, and there are two types: String (owned, growable, heap — the Vec<u8>-with-a-UTF-8-invariant) and &str (a borrowed view: pointer + length, pointing into a String, a literal baked into the binary, or a buffer you own). Because UTF-8 is variable-width, s[0] is deliberately not a thing: indexing by byte could split a character, so you write s.as_bytes()[0], s.chars().next(), or slice on a char boundary — the API makes the O(n) or byte-level nature of what you asked for explicit. Take &str parameters, return String when creating text: exactly the owned/view split C programmers hand-roll with char* plus conventions, and Python hides by making everything an immutable heap object.

The same owned/view split generalises: Vec<T> owns, &[T] is a slice (fat pointer: address + element count, always bounds-checked), PathBuf/&Path, OsString/&OsStr for the platform strings that aren't valid UTF-8. In C terms: Rust took T* + size_t, made it one indivisible value, and checks it. Arrays [T; N] have their length in the type and live wherever you put them, stack included. HashMap<K, V>, BTreeMap, HashSet, VecDeque are in std, generic, and unsurprising; .get() returns Option<&V>, because of course it does.

Closures and iterators. Closures look like |x| x + 1 and capture by the weakest means that works (borrow, mutable borrow, or move). Iterators are lazy and adapter-based — map, filter, fold, zip, enumerate, take, collect — much closer to Python generator pipelines than to TS array methods, except that they compile down to loops with no allocation or virtual dispatch: this is the "zero-cost abstraction" slogan made concrete. for x in &collection borrows, for x in collection consumes it; the difference is in the types, visible at the call site.

Macros exist (println!, vec!, format!) and are hygienic and AST-based, nothing like the C preprocessor: they cannot leak identifiers or unbalance your parentheses, and ! marks them at the call site. You will use standard ones daily and write your own rarely.

4. Traits: interfaces, done as a type system

A trait is a set of methods a type can promise to provide — the closest things in your languages are a TS interface or a Python protocol/abc, with two differences that matter: implementation is explicit and separate from the type definition, and dispatch is usually static.

trait Summary {
    fn summarise(&self) -> String;
    fn teaser(&self) -> String { self.summarise().chars().take(20).collect() }  // default method
}

impl Summary for Article {
    fn summarise(&self) -> String { format!("{} — {}", self.headline, self.author) }
}

Generics are constrained by traits (fn print_all<T: Summary>(items: &[T]), sugar: impl Summary in argument position) and are monomorphised: the compiler stamps out a specialised copy per concrete type, checks the generic body once, at its definition, against the declared bounds, and produces code as fast as hand-written C for each type. If that sounds like C++ templates, it is — except the definition-site checking means errors point at your generic function, not at a 200-line instantiation backtrace, and you do not need to know C++ to use any of it. Dynamic dispatch is opt-in and explicit: Box<dyn Summary> is a fat pointer (data + vtable) for when you genuinely need a heterogeneous collection or a smaller binary.

Things to internalise:

  • #[derive(...)] generates the boring impls — Debug (the {:?} format), Clone, PartialEq, Hash, Copy, Default — structurally, in one line above the type. Half of Rust's convenience lives here.
  • Standard traits are vocabulary. Display (user-facing to_string), Debug (developer-facing), Iterator, From/Into (infallible conversions), AsRef/Borrow (cheap view conversions), Drop (the destructor), Send/Sync (§7). Learning Rust is substantially learning what these names promise.
  • Operator overloading is trait implementation (Add, Index, Deref…), deliberately restricted to that menu; there is no overloading by arity, no getters/setters magic, and field access is just field access.
  • The orphan rule: you may implement your trait for anyone's type, or anyone's trait for your type, but not a foreign trait for a foreign type. This "coherence" guarantees that two crates can never produce conflicting implementations of the same thing — the diamond-dependency nightmare from Python monkey-patching and C++ overload resolution, designed out. The cost: occasionally you must wrap a foreign type in your own one-field struct (a newtype) to implement something on it. Do it; newtypes are also how you get the type system to distinguish a UserId from a SessionId, both wrapping u64, for free at runtime.
  • No inheritance. Reuse is by composition and traits; shared behaviour is a default method or a free function. If you arrive wanting class hierarchies, expect a brief mourning period and then relief.

5. Errors: values, not exceptions

Fallible functions return Result<T, E>. Handling is explicit, and the ? operator makes explicit not mean verbose:

use std::{fs, io};

fn load_config(path: &str) -> Result<Config, io::Error> {
    let text = fs::read_to_string(path)?;   // on Err: return it, converted, now
    let cfg  = parse(&text)?;               // same: propagate or bind the Ok value
    Ok(cfg)
}

? is early-return with error-type conversion (via the From trait), so a function reads as the success path with failure exits at the exact points of failure — the shape of good C with goto cleanup, or of Python with exceptions, but with the failure channel in the signature where callers must acknowledge it. There is no stack-unwinding exception to forget to catch; equally, there is no way to "just let it bubble" without writing ? or naming a type. Errors are ordinary enums you define (often with the thiserror crate generating boilerplate in libraries) or compose dynamically in applications (the anyhow crate's type-erased Result<T>). The ecosystem norm: libraries return precise error types; binaries aggregate.

Panics are the other channel, and they mean "bug": unwrap() on None, indexing out of bounds, arithmetic overflow in debug, an assertion. A panic unwinds and drops everything properly (or aborts, if configured); catching one across a library boundary is possible but considered poor form. Rule of thumb matching Python: Result for the world being disappointing, panic for your own invariants being violated. Note what is absent: no try, no exception hierarchy, no finally — scope-based drop is finally, for every resource, uniformly.

6. A complete small program

Everything above in one file — ownership, borrows in the signature, an iterator pipeline, HashMap with borrowed keys, Result with ?, and not a lifetime annotation in sight (elision infers that the returned words borrow from text, and the compiler checks that callers respect it):

use std::{collections::HashMap, env, error::Error, fs};

fn most_common(text: &str, n: usize) -> Vec<(&str, u32)> {
    let mut counts: HashMap<&str, u32> = HashMap::new();
    for word in text.split_whitespace() {
        let word = word.trim_matches(|c: char| !c.is_alphanumeric());
        if !word.is_empty() {
            *counts.entry(word).or_insert(0) += 1;
        }
    }
    let mut ranked: Vec<(&str, u32)> = counts.into_iter().collect();
    ranked.sort_by(|a, b| b.1.cmp(&a.1).then_with(|| a.0.cmp(b.0)));
    ranked.truncate(n);
    ranked
}

fn main() -> Result<(), Box<dyn Error>> {
    let path = env::args().nth(1).ok_or("usage: wordcount <file>")?;
    let text = fs::read_to_string(path)?;   // an owned String
    for (word, count) in most_common(&text, 10) {   // lent out as &str
        println!("{count:>5}  {word}");
    }
    Ok(())   // text is dropped here; the loop above consumed the borrowed results
}

Note the quiet detail: most_common returns references into a string it does not own. In C this is a loaded gun pointed at whoever frees the buffer first. Here, the (inferred) lifetime ties ranked to text, so using the results after text is dropped is a compile error — the API is safe to offer because the contract is enforced on both sides.

7. Concurrency: the second payoff

"Fearless concurrency" is the marketing phrase; the mechanism is two marker traits. Send means a value may move to another thread; Sync means it may be shared by reference between threads. Nearly all types are Send/Sync automatically, by composition. Rc<T> — single-threaded reference counting, Rust's opt-in equivalent of Python's everything-is-a-counted-reference, minus the atomicity cost — is deliberately neither, so it cannot leak into a thread by accident. To share ownership across threads you reach for Arc<T> (atomic refcount), and to mutate through it, Arc<Mutex<T>>; the Mutex returns a guard whose Drop unlocks, so forgetting to unlock is not expressible, and poisoning (a thread panicked while holding the lock) surfaces as a Result rather than silent corruption.

The consequence that matters: a data race — unsynchronised aliased mutation across threads — is a compile error, because the borrow rules and Send/Sync compose. Deadlocks, livelocks, and racing on logic (two threads politely locking the same mutex to update two fields inconsistently) remain your problem forever. Channels (std::sync::mpsc, and better ones in crates), thread pools (rayon makes a parallel iterator literally .par_iter()), and scoped threads round out the toolkit. For a C programmer who has shipped a heisenbug in a threaded program, this section alone is frequently the reason to learn the language.

Async exists and is heavily used (the tokio runtime powers much of the Rust server ecosystem), but be warned it is the least finished-feeling part of the language: async fn returns a lazy Future (nothing runs until something polls it — closer to a Python generator than to a JS Promise, which starts immediately), there is no executor in std, and you will meet Pin in error messages before you're ready. Learn sync Rust first; async is a second course.

8. unsafe, FFI, and where the floor is

Safety is not mandatory, it is audited. Five extra powers are available inside unsafe { } blocks: dereferencing raw pointers (*const T, *mut T — C pointers, with C's rules and C's perils), calling unsafe functions, accessing mutable statics, implementing unsafe traits, and reading union fields. Crucially, unsafe does not switch off the borrow checker, drop, or bounds logic on safe types; it says "I, the programmer, uphold the invariants the compiler can no longer check, within this block." The standard library is built this way internally, as is every fast crate; the discipline is that unsafe code is encapsulated behind safe APIs whose soundness you argue once — formally, there is even Miri, an interpreter that detects undefined behaviour in unsafe code, something C offers only in much weaker forms (sanitizers). Soundness bugs in an unsafe block are bugs in exactly the way C bugs are, which is the point: the unsafe surface is small, greppable, and reviewable, rather than being the entire program.

Interop is first-class because there is no ABI to impose: Rust has no stable native ABI of its own, so at the boundary you use C's. extern "C" fn, #[repr(C)] structs, std::ffi::{CString, CStr} for NUL-terminated strings, and header/bindgen tooling to generate bindings from C headers make calling C from Rust routine; exposing a Rust library as a .so/.a with a C header is equally routine, and is how Rust has quietly colonised pieces of Firefox, the Linux kernel (which now accepts Rust drivers), Windows, Android, and embedded firmware. Add no_std support — no allocator required, no std, still ownership-checked — and the "systems language" claim is literal, not aspirational.

9. Honest costs, and when to stay away

  • Compile times. Monomorphisation, whole-crate optimisation, and no incremental ABI mean clean release builds of large projects are slow — minutes, not the seconds a C programmer is used to. Incremental debug builds and cargo check (typecheck only, fast) soften this; big teams still feel it.
  • The borrow checker will reject correct programs. It checks a discipline, not the truth; graphs, self-referential structures, and "I mutate through two paths but never simultaneously, trust me" designs fight back. The idiomatic answers — restructure ownership into a tree, use indices into a Vec as graph handles (an arena), or take the runtime-checked Rc<RefCell<T>> — are real design changes, and sometimes Rust loses: a quick script, a throwaway analysis, a CRUD app on a deadline are all still better in Python or TypeScript, and admitting that is part of using Rust well.
  • Expressiveness friction. No function overloading, no default arguments, no variadics, verbose generic bounds, and error messages that — while genuinely the best in the business — can run to a page for a misplaced &. The learning curve is steepest in weeks 1–4 and is mostly unlearning "share everything" habits from Python/TS and "track it in my head" habits from C.
  • Ecosystem gaps. GUIs, gamedev tooling, and data-science are years behind Python/JS in breadth (though serde for serialisation, the clap CLI parser, reqwest, tokio, axum, and sqlx are best-in-class where they exist). Expect to find a crate; check its maintenance before depending on it.

Rust earns its keep where the failure modes it eliminates are the ones that hurt you: long-lived services, parsers of untrusted input, concurrent infrastructure, anything memory-unsafe in C today, and anything where Python is too slow but rewriting in C feels like malpractice.

  1. rustup in, cargo new, and rewrite a small C or Python utility you already understand — the word-counter in §6 is a good template. Reach for &str/&[T] parameters and owned returns.
  2. When the borrow checker complains, read the whole error; it usually names the conflicting borrows and suggests the fix. Clone deliberately, note where, and revisit each clone after the program works — most dissolve once ownership is restructured.
  3. Force the standard traits early: #[derive(Debug, Clone, PartialEq)] on everything, implement Display and From by hand once, write one generic function with a trait bound and one Box<dyn Trait>.
  4. Write tests in-file with #[test]; run cargo clippy and treat it as a patient senior reviewer. It is, effectively, the community's style-and-correctness consensus, executable.
  5. Skip async, macros, and clever lifetime gymnastics until a real program demands them.

The canonical next step is The Rust Programming Language ("the Book", free at doc.rust-lang.org/book) — chapters 4, 6, 10, and 16 deepen exactly §2, §3, §4, and §7 of this document — with Rust by Example for syntax lookup and the std docs as a permanent browser tab. You already know how computers work and how type systems feel; what Rust adds is one idea, enforced very thoroughly. Once ownership stops being a rule you obey and becomes the way you sketch designs on a whiteboard, the rest of the language reads as a well-stocked standard library attached to it.

Rust for C, Python, and TypeScript Programmers

Rust is a systems programming language with C-like control over memory and performance, but without requiring you to establish memory safety by hand. It has no garbage collector, no required runtime, and no undefined-behavior-by-default memory model. Its central idea is simple: the compiler tracks ownership and borrowing so that memory can be reclaimed deterministically without data races or dangling pointers.

That safety is not achieved by making everything dynamic. Rust also has generics, algebraic data types, pattern matching, type inference, closures, and a capable package manager. The result often feels like a statically typed, expression-oriented language with a C backend and an unusually strict code reviewer.

This introduction assumes you can read C and have used Python and TypeScript. It emphasizes the parts whose mental models differ most.

1. The toolchain and the shape of a program

Install Rust with rustup, which manages compiler versions and targets. The standard workflow uses Cargo, both build tool and package manager:

cargo new hello       # binary package
cd hello
cargo run             # build and run
cargo test            # build and run tests
cargo check           # fast type/borrow checking, no final binary

A minimal program is already revealing:

fn main() {
    let name = "Ada";
    let mut count = 0; // `mut` permits reassignment

    for _ in 0..3 {
        count += 1;
        println!("Hello, {name}!");
    }

    assert_eq!(count, 3);
}

Bindings are immutable by default; mut opts into mutation. This is narrower than C++ const: it controls whether that binding may be changed, not whether every reachable object is immutable.

Rust is expression-oriented. Blocks have values, and the final expression without a semicolon is returned:

fn classify(n: i32) -> &'static str {
    if n < 0 {
        "negative"
    } else if n == 0 {
        "zero"
    } else {
        "positive"
    }
}

There is no implicit integer-to-boolean conversion and no fallthrough switch; conditions must be bool.

Common scalar types include i32, u64, usize (pointer-sized, mainly for indexing), f64, bool, and char (a Unicode scalar value, not a byte). Fixed-size arrays are [T; N]; tuples are (T, U). Integer overflow is a programming error: debug builds normally panic, while release builds wrap unless overflow checks are enabled. Use wrapping_add, checked_add, or saturating_add when another behavior is intended.

The standard integer types are exact about width. Unlike C, ordinary signed overflow is never a license for the optimizer to assume it cannot happen.

2. Ownership: the central idea

Every Rust value has one owner. When the owner goes out of scope, the value is dropped. A value can be moved to a new owner, but the old binding can no longer be used.

fn main() {
    let a = String::from("hello");
    let b = a;              // move: b now owns the allocation
    // println!("{a}");     // compile error
    println!("{b}");
}                            // b's String is freed here

For a heap string, assignment does not deep-copy and does not leave two owners pointing at one allocation. It transfers ownership. This is closer to C++ move semantics than to Python or TypeScript assignment, except that the compiler prevents use of the moved-from variable.

Small values with fully value-like semantics implement Copy:

let x = 5;
let y = x; // copies; x remains usable

Integers, floats, booleans, characters, and tuples/arrays of Copy values are examples. String and Vec<T> are not. Calling .clone() requests an explicit, potentially expensive deep copy when the type supports it.

Ownership gives destruction a precise, deterministic order. Rust's Drop trait is its destructor mechanism, commonly used for files, sockets, locks, and heap allocations. There are no finalizers whose timing depends on a garbage collector.

Borrowing instead of transferring

Usually a function only needs temporary access:

fn length(s: &String) -> usize {
    s.len()
}

fn main() {
    let text = String::from("hello");
    let n = length(&text); // borrow, not move
    println!("{text} has {n} bytes");
}

&T is a shared reference. &mut T is an exclusive reference:

fn push_world(s: &mut String) {
    s.push_str(", world");
}

let mut text = String::from("hello");
push_world(&mut text);

The essential rule is:

At any time, a value may have any number of shared references or one exclusive reference—but not both.

References must also never outlive what they point to. These two rules prevent use-after-free, iterator invalidation through many common APIs, and data races. They also explain many initial compiler errors: Rust rejects aliases when mutation could invalidate another view, even in single-threaded code.

The borrow checker is flow-sensitive and understands non-lexical lifetimes. A borrow ends after its last use, not necessarily at the closing brace:

let mut v = vec![1, 2, 3];
let first = &v[0];
println!("{first}");
v.push(4); // OK: `first` is no longer used
// println!("{first}"); // moving this above `push` would be an error

One practical rule: prefer functions that take borrowed data, and return owned data when the caller should keep it. Do not preemptively clone everything—but an occasional explicit clone is often clearer than contorting an API to avoid it.

3. Strings, arrays, and slices

Rust distinguishes owning containers from borrowed views:

Owned Borrowed view Meaning
String &str UTF-8 text
Vec<T> &[T] contiguous elements
PathBuf &Path filesystem path

A slice contains a pointer and length; it does not own its elements. Slices let one function accept data from a vector, array, or subrange:

fn sum(xs: &[i32]) -> i32 {
    xs.iter().sum()
}

let a = [1, 2, 3, 4];
assert_eq!(sum(&a), 10);
assert_eq!(sum(&a[1..3]), 5);

A String is a growable UTF-8 buffer. A &str is a borrowed UTF-8 view. Prefer &str for read-only function parameters and String for owned results, unless there is a reason to be more specific.

Rust strings are not arrays of Unicode characters. s.len() is a byte count, and indexing by an arbitrary integer is forbidden because it could split a UTF-8 encoding. Use .chars(), .bytes(), or slicing at known character boundaries. This is different from Python's Unicode-code-point indexing and TypeScript's UTF-16 code-unit strings.

4. Data modeling: structs, enums, and exhaustive matching

Structs are product types, similar to C structs or TypeScript object types:

struct User {
    id: u64,
    name: String,
    active: bool,
}

Methods live in impl blocks. &self borrows the receiver, &mut self borrows it exclusively, and self consumes it:

impl User {
    fn display_name(&self) -> &str {
        &self.name
    }

    fn deactivate(&mut self) {
        self.active = false;
    }
}

Enums are tagged unions, not just integer constants. Each variant can carry different data:

enum Message {
    Quit,
    Move { x: i32, y: i32 },
    Write(String),
}

fn describe(message: &Message) -> String {
    match message {
        Message::Quit => "quit".to_owned(),
        Message::Move { x, y } => format!("move to {x}, {y}"),
        Message::Write(text) => format!("write {text}"),
    }
}

match must be exhaustive. This is Rust's answer to the fragile combination of C unions plus tags, and it resembles TypeScript discriminated unions—but the representation is native and the compiler checks all variants without relying on a separately written discriminator field.

Patterns can destructure structs, tuples, references, ranges, and nested enums. if let handles one interesting case; let ... else is useful for early returns.

No null references

Optional values use Option<T>:

enum Option<T> {
    Some(T),
    None,
}

You must handle absence before accessing the value:

fn first_even(xs: &[i32]) -> Option<i32> {
    xs.iter().copied().find(|x| x % 2 == 0)
}

match first_even(&[1, 3, 6, 8]) {
    Some(n) => println!("found {n}"),
    None => println!("none found"),
}

Combinators such as .map(), .and_then(), .unwrap_or(), and .ok_or() keep optional pipelines concise. Avoid reflexively calling .unwrap(): it panics on None and often hides an error path that should be designed.

5. Errors are values; panics are not normal errors

Recoverable failures use Result<T, E>:

use std::fs;
use std::io;

fn read_config(path: &str) -> Result<String, io::Error> {
    let text = fs::read_to_string(path)?;
    Ok(text.trim().to_owned())
}

Result<T, E> is either Ok(T) or Err(E). The ? operator returns an error early, converting it when the error types support the required conversion. It is the normal way to propagate errors, not hidden exception machinery.

This explicitness resembles Go's error returns more than Python exceptions, but combinators and ? remove most repetition. Libraries often expose structured error enums. Applications commonly use a crate such as anyhow for convenient contextual errors, while thiserror helps define library error types.

panic! indicates a bug, violated invariant, or unrecoverable condition. By default it unwinds the thread; builds can instead abort. Do not use panics for routine malformed user input. Indexing out of bounds, unwrap() on None/Err, and failed assertions panic. Prefer checked alternatives such as slice.get(i) when invalid input is expected.

Unlike C, there is no need to pair every return code with manual cleanup: ownership still drops values during early returns and unwinding.

6. Generics and traits

Rust generics are compile-time parameterized, like C++ templates but with declared interface bounds:

fn largest<T: PartialOrd>(xs: &[T]) -> Option<&T> {
    let mut result = xs.first()?;
    for item in &xs[1..] {
        if item > result {
            result = item;
        }
    }
    Some(result)
}

A trait defines shared behavior:

trait Summary {
    fn summary(&self) -> String;
}

fn notify(item: &impl Summary) {
    println!("{}", item.summary());
}

Traits support default methods, associated types, generic implementations, and operator overloading. impl Trait in an argument is shorthand for a generic parameter. In return position it means “some concrete type implementing this trait,” which is especially useful for iterators and closures.

Normal generic calls are monomorphized: the compiler generates specialized code for each used type. This preserves static dispatch and enables inlining, but can increase code size. Unlike TypeScript, types exist during compilation, not at runtime; there is no general runtime reflection over a generic T.

For heterogeneous values or dynamic plugin-like boundaries, use a trait object:

fn notify_all(items: &[&dyn Summary]) {
    for item in items {
        println!("{}", item.summary());
    }
}

dyn Summary uses dynamic dispatch, typically through a vtable, and is unsized, so it appears behind a pointer such as &dyn Summary, Box<dyn Summary>, or Arc<dyn Summary>.

The standard traits are worth learning early: Debug and Display for formatting, Clone/Copy, Default, PartialEq/Eq, PartialOrd/Ord, Iterator, From/Into, and Deref. Most are derivable:

#[derive(Debug, Clone, PartialEq)]
struct Point { x: f64, y: f64 }

There is no class inheritance. Composition, generics, and traits provide polymorphism instead.

7. Lifetimes: describing borrowed relationships

Every reference has a lifetime, but the compiler infers most of them. Explicit lifetime annotations become necessary when a function or type stores/returns references and the relationship is ambiguous:

fn longer<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() >= y.len() { x } else { y }
}

This does not make anything live longer. It says the returned reference is valid for the overlap of the inputs' lifetimes, preventing it from being used after either source expires.

A struct holding a reference likewise needs a parameter:

struct Line<'a> {
    text: &'a str,
}

'static means valid for the whole program, not “global mutable variable.” String literals are &'static str because their bytes live in the binary. Owned String and Vec<T> values often avoid lifetime parameters entirely.

If lifetime annotations begin spreading through a design, reconsider ownership: return an owned value, pass an index, or restructure the data flow. Lifetimes describe a solution; they are not themselves a memory-management strategy.

8. Collections, closures, and iterators

Vec<T> is a growable contiguous array, roughly a C++ std::vector or Python list without heterogeneous elements. Other common collections include HashMap, BTreeMap, VecDeque, and BinaryHeap.

Closures capture their environment by borrowing, mutable borrowing, or moving as required:

let threshold = 10;
let large: Vec<i32> = (0..100)
    .filter(|n| n > &threshold)
    .map(|n| n * 2)
    .collect();

Iterators are lazy. collect() drives the pipeline and builds the requested collection. The optimizer can turn such code into loops competitive with handwritten C; these are often called zero-cost abstractions, meaning you do not pay for an unused generality or an implicit per-element heap allocation.

For mutation, use .iter_mut(); for consuming an owned collection, use .into_iter(). A plain for x in &xs borrows, for x in &mut xs mutably borrows, and for x in xs consumes.

Borrow rules make it invalid to structurally modify most collections while iterating over them. Collect changes first, retain elements with .retain(), or use indices where appropriate.

9. Smart pointers and interior mutability

Most data needs no pointer type beyond ordinary ownership and references. When it does, the choice communicates semantics:

  • Box<T>: one owner, heap allocation; also used for recursive types and trait objects.
  • Rc<T>: reference-counted shared ownership, single-threaded.
  • Arc<T>: atomic reference-counted shared ownership, thread-safe when T permits it.
  • RefCell<T>: borrow rules checked at runtime, single-threaded.
  • Mutex<T> / RwLock<T>: synchronized mutable access across threads.
  • Cell<T>: simple single-threaded mutation for suitable small values.

RefCell and Cell provide interior mutability: mutation through an otherwise shared outer value. RefCell tracks active borrows dynamically and panics if rules are violated; it does not circumvent thread safety.

A common single-threaded pattern is Rc<RefCell<T>>; a common multithreaded pattern is Arc<Mutex<T>>. Neither is the default answer to a borrow-checker error. Shared mutable graphs may justify them, but ordinary tree-like ownership is simpler and faster.

Reference counting does not by itself collect cycles. Long-lived cyclic structures need weak references (Weak) or a different representation, such as IDs into an arena.

10. Concurrency and asynchronous Rust

The same ownership rules make many races impossible. The marker traits Send and Sync describe whether types can cross thread boundaries or be shared between threads. Rc<T>, for example, is deliberately not Send; Arc<T> is its atomic counterpart.

Threads own or borrow data according to explicit scopes:

use std::thread;

let numbers = vec![1, 2, 3, 4];
let total = thread::scope(|s| {
    let handle = s.spawn(|| numbers.iter().sum::<i32>());
    handle.join().unwrap()
});
assert_eq!(total, 10);

Scoped threads can safely borrow stack data because the scope waits for them. thread::spawn requires owned or 'static data, often via move closures. Channels, mutexes, and atomics cover other coordination styles. Rust prevents data races, not all race conditions, deadlocks, or logic errors.

Async Rust is a separate facility, not automatically parallel code. An async fn returns a lazy Future; an executor must poll it. .await yields when work cannot make progress. Tokio is a common production runtime, especially for network services, while the language and standard library deliberately leave the executor choice open.

Use OS threads for CPU-bound parallel work and async tasks for large numbers of mostly waiting operations. Async adds important constraints around cancellation, pinned self-referential futures, runtime compatibility, and holding locks across .await; it is not necessary for every program.

11. unsafe: an audit boundary, not a different language

Safe Rust prevents memory unsafety. unsafe permits a small set of additional operations, including dereferencing raw pointers, calling unsafe functions, and accessing mutable statics. It is needed for some FFI, hardware access, custom allocators, and low-level data structures.

let mut x = 5;
let p = &mut x as *mut i32;

unsafe {
    *p += 1;
}
assert_eq!(x, 6);

unsafe does not disable the borrow checker or make arbitrary code safe. It tells the compiler: “I have established invariants that you cannot verify.” Keep unsafe blocks small, document their safety requirements, and expose a safe API whose callers cannot cause undefined behavior.

Rust still has undefined behavior if unsafe code violates the language's rules. The difference is that responsibility is localized and auditable rather than spread across every pointer operation.

For C interoperability, Rust can call C functions and expose C ABI functions, but types, ownership transfer, strings, panics, and threading rules must be handled explicitly at the boundary. bindgen and cbindgen can generate declarations. Cross-language boundaries are usually where the real design work lies.

12. Packages, modules, testing, and performance

A crate is a compilation unit: a library or binary. A package is a Cargo project containing one or more crates. Third-party packages are published on crates.io and declared in Cargo.toml:

[dependencies]
serde = { version = "1", features = ["derive"] }

Modules organize code and privacy. Items are private to their module by default; pub exposes them. use imports paths, while mod declares module structure. Integration tests live in tests/; unit tests often sit beside implementation code:

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn sums_even_numbers() {
        let xs = [1, 2, 3, 4];
        assert_eq!(xs.iter().filter(|x| **x % 2 == 0).sum::<i32>(), 6);
    }
}

cargo fmt formats code, cargo clippy provides lints, and rustdoc builds documentation from /// comments, including tests embedded in examples.

Performance work should feel familiar to a C programmer: values have known layouts subject to representation rules, allocation is visible, and you can control data structures and concurrency. The compiler is LLVM-based and performs aggressive optimization. Still, “safe” does not mean “automatically fastest”: clones, reference counting, allocations, dynamic dispatch, and excessive abstraction can all cost time. Profile before optimizing.

For embedded and other minimal environments, no_std removes the standard library while retaining the core language and the core library. Allocation is then explicit through alloc where available.

13. How to think when coming from other languages

From C: keep your understanding of memory layout, caches, syscalls, and zero-copy design. Stop treating pointer validity, aliasing, initialization, and cleanup as conventions; Rust encodes many of them in types. Prefer slices and references to raw pointer-plus-length pairs, and Option/Result to sentinel values.

From Python: variables are not generally names attached to shared heap objects. Values have owners, types are fixed after inference, and mutation through aliases is deliberately constrained. The compiler replaces many runtime checks and tests, but dynamic designs may need enums, trait objects, or arenas rather than “a dictionary containing anything.”

From TypeScript: structural-looking data is usually nominal by type definition, generics survive as generated machine code rather than being erased into JavaScript, and exhaustive enums are first-class values. Rust's Option resembles strict null checking, but ownership has no direct TypeScript counterpart. Also, Rust has no prototype chain or arbitrary runtime object shape changes.

The most useful adjustment is to design data flow before code:

  1. Who owns each value?
  2. Who merely reads it, and for how long?
  3. Where is mutation necessary?
  4. Is absence or failure part of the domain?
  5. Can an enum make invalid states unrepresentable?

If you answer those questions first, the compiler becomes a design assistant rather than an obstacle.

14. A small example that ties it together

use std::collections::HashMap;
use std::io;

#[derive(Debug)]
struct Record {
    name: String,
    score: i32,
}

fn best_record(records: &[Record]) -> Option<&Record> {
    records.iter().max_by_key(|r| r.score)
}

fn scores_by_name(records: &[Record]) -> HashMap<&str, i32> {
    records
        .iter()
        .map(|r| (r.name.as_str(), r.score))
        .collect()
}

fn load(path: &str) -> Result<Vec<Record>, Box<dyn std::error::Error>> {
    let input = std::fs::read_to_string(path)?;
    let mut records = Vec::new();

    for line in input.lines() {
        let (name, score) = line
            .split_once(',')
            .ok_or_else(|| io::Error::new(io::ErrorKind::InvalidData, "expected name,score"))?;
        records.push(Record {
            name: name.trim().to_owned(),
            score: score.trim().parse()?,
        });
    }
    Ok(records)
}

load owns its input buffer only while parsing, and each Record owns its name. The returned vector owns all records. best_record returns a view tied to the input slice, with its lifetime inferred. scores_by_name returns an owned map containing borrowed names, so the records must remain alive while that map is used. Errors from I/O, malformed lines, and integer parsing propagate through ?; no manual cleanup or null checks are needed.

This is idiomatic Rust in miniature: ownership is explicit in the types, borrowing avoids copies, variants model failure, and the compiler checks the relationships across function boundaries.

What to learn next

Start with small, owned-data programs: a CLI parser, file indexer, or log analyzer. Then add borrowed views, custom errors, and tests. Postpone elaborate lifetime-heavy structures, async frameworks, and unsafe data structures until ordinary ownership feels natural.

The best next resources are the official Rust Book, the example-driven Rust by Example, and the standard library documentation. For compiler errors, read the whole diagnostic and experiment with a smaller case: Rust's longest errors often point directly at an ownership decision worth reconsidering.

Rust's learning curve is real, but its payoff is not merely “the compiler catches bugs.” It gives you a vocabulary for resource ownership, failure, and sharing that remains useful in every language—even when that language cannot enforce it.

Rust for People Who Already Know C, Python and TypeScript

About a 15–20 minute read. It assumes you know what a pointer, a vtable, a closure, a generic and an event loop are, and spends its time on what's actually new.

The one-paragraph version

Rust is a compiled systems language with no garbage collector and a runtime about the size of C's. You get C's control over memory layout and C-level performance. The type system will feel familiar from TypeScript and ML: sum types, generics, type inference. Unlike TypeScript's, it is sound and is used for code generation. The tooling feels like what Python and JS have been converging on (uv, npm), only more consistent. What's new is the ownership and borrowing discipline. Every heap allocation has exactly one owner, which frees it automatically. Every other pointer is a borrow, and the compiler proves at compile time that no borrow outlives what it points to and that nothing is mutated while it is aliased. That one rule rules out use-after-free, double free, iterator invalidation and data races, at zero runtime cost. Most of the rest of the language exists to make that rule comfortable to live with.

If you've used uv or ruff in Python, or swc, Biome or Turbopack in JS, you've already run Rust programs.

1. Tooling: cargo does everything

curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh   # installs rustup, rustc, cargo
cargo new hello && cd hello
cargo run                 # debug build + run
cargo build --release     # optimized build -> target/release/hello
cargo test                # unit + integration + doc tests
cargo clippy              # linter (very good, use it)
cargo fmt                 # formatter (no style debates)
cargo add serde --features derive   # add a dependency from crates.io
cargo doc --open          # HTML docs for your code and all dependencies

Cargo.toml is your package.json / pyproject.toml. Cargo.lock pins exact versions. The edition field (edition = "2024") selects a language dialect. Crates on different editions link together fine, so editions can fix syntax without splitting the ecosystem. There's no header/include system, no Makefile, and no separate venv or node_modules dance. A crate is the compilation unit, the output is usually a single static binary, and cross-compiling is usually just rustup target add.

2. Basics, quickly

fn main() {
    let x = 5;                 // immutable by default, type inferred (i32)
    let mut count: u64 = 0;    // `mut` opts in to mutation
    count += 1;

    let x = x * 2;             // shadowing: a new binding that reuses the name
    let label = if x > 5 { "big" } else { "small" };   // `if` is an expression

    let total = {              // so is a block: its value is its last expression
        let a = 3;
        a * x                  // no semicolon -> this is the block's value
    };

    for i in 0..3 { println!("{i}"); }          // ranges are half-open
    let squares: Vec<i32> = (1..=5).map(|n| n * n).collect();
    println!("{label} {total} {count} {squares:?}");    // `!` marks a macro
}

fn add(a: i32, b: i32) -> i32 {
    a + b                      // last expression is the return value
}

Things that will surprise you:

  • Scalar types are explicit: i8…i128, u8…u128, isize/usize (pointer-sized, used for indexing), f32/f64, bool, and char (a 4-byte Unicode scalar value, not a byte).
  • There are no implicit numeric conversions. Even i32 + i64 is a compile error. Use as for C-style casts (which truncate silently) or u8::try_from(x)? for checked ones.
  • Overflow panics in debug builds and wraps in release builds. When you care, say what you mean: a.wrapping_add(b), a.checked_add(b) (returns Option), a.saturating_add(b).
  • Strings are UTF-8, and there are two main types: String (owned, growable, on the heap) and &str (a borrowed view). You can't write s[3], because a byte index into UTF-8 doesn't mean "the third character". Use s.chars(), s.bytes(), or byte-range slices like &s[0..3] (which panic if they split a character).
  • There is no null, no undefined, no exceptions, no inheritance, no function overloading, and no default arguments. Each one has a replacement, covered below.

3. Structs, enums and match

Structs and methods

#[derive(Debug, Clone, PartialEq)]     // auto-generate printing, copying, ==
struct Point { x: f64, y: f64 }

impl Point {
    fn new(x: f64, y: f64) -> Self { Point { x, y } }   // a convention, not a constructor
    fn norm(&self) -> f64 { (self.x * self.x + self.y * self.y).sqrt() }
    fn scale(&mut self, k: f64) { self.x *= k; self.y *= k; }
}

Data and behaviour are declared separately. A struct is laid out like a C struct (the compiler may reorder fields unless you write #[repr(C)]), and impl blocks attach functions to it. The receiver is spelled out: &self borrows the value immutably, &mut self borrows it mutably, and plain self takes ownership (consumes it). This is Python's explicit self, with the access mode in the signature.

Enums are real sum types

In C you write a tagged union and hope everyone checks the tag. In TypeScript you write a discriminated union and the checker helps, as long as nobody lies with as. In Rust the tagged union is a language primitive, and the compiler makes sure you check the tag before you can reach the payload:

enum Shape {
    Circle { r: f64 },
    Rect { w: f64, h: f64 },
    Empty,
}

fn area(s: &Shape) -> f64 {
    match s {                                   // must be exhaustive
        Shape::Circle { r } => std::f64::consts::PI * r * r,
        Shape::Rect { w, h } if w == h => w * w, // guards
        Shape::Rect { w, h } => w * h,
        Shape::Empty => 0.0,
    }
}

Add a variant and every match that doesn't handle it stops compiling. This is the main reason Rust refactors feel safe.

Option replaces null

null is gone. A value that might be absent has type Option<T>, which is just an ordinary enum from the standard library:

enum Option<T> { Some(T), None }     // (already in the prelude, don't define it)

fn find(names: &[&str], target: &str) -> Option<usize> {
    names.iter().position(|n| *n == target)
}

match find(&names, "bob") {
    Some(i) => println!("found at {i}"),
    None => println!("nope"),
}
if let Some(i) = find(&names, "bob") { println!("{i}"); }       // one-armed match
let Some(i) = find(&names, "bob") else { return; };             // early exit
let i = find(&names, "bob").unwrap_or(0);                       // combinators

You can't use an Option<usize> as a usize by accident. A C programmer will want to know the cost: Option<&T> and Option<Box<T>> are guaranteed to be the same size as a raw pointer, with None stored as the null bit pattern. So you get null's representation without null's bugs.

4. Ownership: the actual new idea

Here are the rules. They're short:

  1. Every value has exactly one owner, which is a variable, a struct field, a Vec slot and so on.
  2. When the owner goes out of scope, the value is dropped: its destructor runs and its memory is freed. This is deterministic, like C++ RAII or a perfectly reliable free.
  3. Assignment, passing by value and returning by value move ownership. The source becomes unusable.

First, what these types look like in memory. There are no surprises here for a C programmer:

A String is a {ptr, len, cap} triple pointing at a heap buffer, and a Vec<T> is the same thing. A &str is a {ptr, len} pair pointing into someone else's buffer. A Box<T> is a single non-null pointer to a heap allocation. Rust hides none of this, and you can reason about it exactly as you would in C.

Now, what happens on assignment:

let a = String::from("hi");
let b = a;              // move: copies 3 words, `a` is now dead
// println!("{a}");     // error[E0382]: borrow of moved value: `a`
let c = b.clone();      // explicit deep copy, a second heap buffer

Compare the three languages:

  • C: b = a copies the struct. Now two pointers own one buffer, and freeing both is a double free.
  • Python/TS: b = a copies a reference and bumps a refcount, or leaves it to a tracing GC. Now two names alias one mutable object.
  • Rust: b = a copies the struct, and the compiler statically forgets a. One owner, one free, no aliasing, no runtime bookkeeping.

Types that are just plain bits with no destructor (integers, floats, bool, char, &T, and tuples or arrays of these) implement the Copy trait. Assigning one copies it and leaves the source usable, as in C. A struct you write can opt in with #[derive(Clone, Copy)] if all its fields are Copy. Anything else needs an explicit .clone(), so expensive copies are always visible in the code.

Passing by value moves too:

fn consume(s: String) { /* s is dropped (freed) at the end of this function */ }

let s = String::from("x");
consume(s);
// s is gone here. Moving ownership in and out of every function
// would be unbearable, which is why borrowing exists.

5. Borrowing: references with rules

A reference lets you use a value without taking ownership. There are two kinds:

Syntax How many at once Can mutate? Closest analogue
Shared borrow &T any number no* const T * that really means it
Exclusive borrow &mut T exactly one, and no &T at the same time yes T * restrict that is actually enforced

*Except through explicit "interior mutability" types, covered in section 10.

The core rule is aliasing XOR mutability: at any point, a value has either any number of readers or exactly one writer. The second rule is that a reference can never outlive the value it points to.

fn total_len(words: &[String]) -> usize {   // borrows; caller keeps ownership
    words.iter().map(|w| w.len()).sum()
}
fn shout(s: &mut String) { s.make_ascii_uppercase(); }

let mut v = vec![String::from("a"), String::from("b")];
let n = total_len(&v);      // &v: a shared borrow, ends when the call returns
shout(&mut v[0]);           // &mut: an exclusive borrow

Why bother, even in single-threaded code? Here is a bug every C programmer has written:

int *first = &v->data[0];
vec_push(v, 4);          /* may realloc -> `first` now dangles */
printf("%d\n", *first);  /* use-after-free */

The Rust equivalent doesn't compile. A borrow lasts from where it's created to where it's last used (not to the end of the scope), and a &mut borrow (push needs one) can't overlap a live & borrow:

error[E0502]: cannot borrow `v` as mutable because it is also borrowed as immutable
  |     let last = &v[3];
  |                 - immutable borrow occurs here
  |     v.push(5);
  |     ^^^^^^^^^ mutable borrow occurs here
  |     println!("{last}");
  |                ---- immutable borrow later used here

The same rule catches "modifying a dict while iterating over it" (a runtime RuntimeError in Python) and its equivalents in every other language, at compile time. As a bonus, since &mut is guaranteed unaliased, the optimizer gets restrict semantics everywhere for free.

Slices are borrowed views into contiguous memory: &[T] into a Vec<T> or an array, and &str into a String. Idiomatic functions take slices (&str, &[T]) and return owned values (String, Vec<T>). That makes them accept the widest range of inputs and keeps ownership simple.

6. Lifetimes: naming how long borrows live

Usually the compiler works out how long references live without help. You have to write it down when a function returns a reference and the compiler can't tell which input it came from:

fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

'a is a generic parameter, like T, except it ranges over regions of code rather than types. The signature says: "the result is valid for as long as both inputs are." Lifetimes don't change what the program does. They are claims the compiler checks, and they produce no code. The caller then can't use the result after either input dies.

Structs that hold references need a lifetime parameter too, because the struct can't outlive what it borrows:

struct Parser<'src> { input: &'src str, pos: usize }

'static means the value lives for the entire program, as string literals and leaked allocations do.

Practical advice: when lifetimes in your structs get hairy, store owned data (String instead of &str, Vec<T> instead of &[T]). Borrowing is most natural for function arguments and short-lived views. Long-lived data structures usually own their contents.

7. Error handling: Result and ?

Rust has no exceptions. A function that can fail returns Result<T, E>, an enum with the variants Ok(T) and Err(E). The ? operator unwraps an Ok, and on an Err returns early from the function, converting the error type via the From trait if needed:

use std::{fs, num::ParseIntError};

#[derive(Debug)]
enum ConfigError { Io(std::io::Error), Parse(ParseIntError) }

impl From<std::io::Error> for ConfigError {
    fn from(e: std::io::Error) -> Self { ConfigError::Io(e) }
}
impl From<ParseIntError> for ConfigError {
    fn from(e: ParseIntError) -> Self { ConfigError::Parse(e) }
}

fn read_port(path: &str) -> Result<u16, ConfigError> {
    let text = fs::read_to_string(path)?;     // io::Error -> ConfigError
    let port = text.trim().parse::<u16>()?;   // ParseIntError -> ConfigError
    Ok(port)
}

This is Go's if err != nil with the boilerplate collapsed into one character, while every fallible call stays visible. Compare C's "check errno, maybe" and Python/TS's "anything might throw". In practice:

  • Libraries define an error enum, usually with the thiserror crate generating the From and Display impls above.
  • Applications use anyhow::Result<T>, which holds any error, adds context (.context("reading config")?) and makes main print a readable chain.
  • panic! is for bugs, not expected failures: broken invariants, out-of-bounds indexing, .unwrap() on None. It unwinds the thread, running destructors, and is closer to assert or abort() than to throw. You don't use it for control flow.

.unwrap() and .expect("why this can't fail") turn a Result or Option into a panic. That's fine in prototypes and tests. In production code, treat each one as an assertion that should be justified.

8. Traits and generics

A trait is an interface: a set of methods a type promises to provide. It's close to a TS interface or a Python Protocol, with two differences. It is nominal: you write impl Trait for Type explicitly. And you can implement your own traits for types you didn't write, including i32 and Vec<T>.

trait Describe {
    fn name(&self) -> String;
    fn describe(&self) -> String {               // default method
        format!("<{}>", self.name())
    }
}

impl Describe for Point { fn name(&self) -> String { format!("({}, {})", self.x, self.y) } }
impl Describe for i32   { fn name(&self) -> String { self.to_string() } }

There are two ways to be polymorphic over a trait. The trade-off is the classic C one, macro-expanded code versus function pointers:

// Static dispatch: monomorphized. One copy compiled per concrete T, calls inlined.
// Type-checked at the definition, unlike C++ templates or C macros.
fn print_all<T: Describe>(items: &[T]) {
    for it in items { println!("{}", it.describe()); }
}
fn print_one(x: &impl Describe) { println!("{}", x.describe()); } // sugar for the above

// Dynamic dispatch: a trait object. `&dyn Describe` is a fat pointer
// (data ptr, vtable ptr), exactly the C "struct of function pointers" pattern.
fn print_mixed(items: &[Box<dyn Describe>]) {
    for it in items { println!("{}", it.describe()); }
}
let things: Vec<Box<dyn Describe>> = vec![Box::new(42), Box::new(Point::new(1.0, 2.0))];
print_mixed(&things);

Much of the standard library's behaviour comes from a handful of traits, most of which you get with #[derive(...)]:

Trait Gives you Python / TS analogue
Debug {:?} formatting __repr__
Display {} formatting, .to_string() __str__ / toString()
Clone / Copy .clone() / implicit bitwise copy copy.deepcopy-ish / value types
PartialEq, Eq, PartialOrd, Ord, Hash ==, <, use as HashMap key __eq__, __lt__, __hash__
Default T::default() default constructor
From / Into conversions, used by ? –
Iterator for loops and all adaptor methods __iter__ / __next__, [Symbol.iterator]
Drop a destructor __del__ (but deterministic)
Add, Mul, Index, … operator overloading __add__, __getitem__
Send, Sync safe to move or share across threads – (see section 11)

There's no inheritance. You build behaviour by composing structs and implementing traits. A trait can require another (trait Shape: Describe { … }), which covers most of what you'd want inheritance for.

9. Closures and iterators

Closures look like |x| x + 1. Each one is an anonymous struct holding its captured variables. Which of three traits it implements depends on what it does with them:

  • Fn: only reads its captures, so it can be called any number of times, even concurrently.
  • FnMut: mutates its captures, so calls need exclusive access.
  • FnOnce: consumes its captures, so it can only be called once.

Write move |x| … to make the closure take ownership of what it captures. You need this when the closure outlives the current stack frame, for example when it's passed to a thread or returned from a function.

Iterators are lazy, like Python generators. They're built from adaptors and then consumed:

use std::collections::HashMap;

let text = "the quick brown fox jumps over the lazy dog the end";
let mut freq: HashMap<&str, usize> = HashMap::new();
for w in text.split_whitespace() {
    *freq.entry(w).or_insert(0) += 1;
}
let mut top: Vec<_> = freq.into_iter().filter(|&(_, n)| n > 1).collect();
top.sort_by(|a, b| b.1.cmp(&a.1));

All of this is monomorphized and inlined, so a chain like .iter().filter().map().sum() usually compiles to the same machine code as a hand-written C loop, often with fewer bounds checks. There are three ways to iterate a collection, and they correspond to the three ownership modes:

  • v.iter() yields &T.
  • v.iter_mut() yields &mut T.
  • v.into_iter() (what for x in v does) yields T and consumes v.

10. Heap, sharing and "interior mutability"

Single ownership plus borrowing covers most code. For the rest there's a small toolbox of library types. Each one relaxes a rule in a specific, visible way:

Type What it is You'd use it for Mental model
Box<T> unique owning heap pointer recursive types, trait objects, large values malloc + guaranteed free
Vec<T>, String, HashMap<K,V> growable owned collections everyday data –
Rc<T> refcounted shared ownership, single-threaded graphs, shared immutable data a Python object (cycles leak; break them with Weak<T>)
Arc<T> Rc with atomic refcount sharing across threads std::shared_ptr
Cell<T>, RefCell<T> mutation through a shared & caches, mutable state in an Rc borrow rules checked at runtime (RefCell panics on a violation)
Mutex<T>, RwLock<T> RefCell for threads shared mutable state a lock that contains the data
OnceLock<T>, LazyLock<T> initialize once globals, lazily computed config pthread_once

Rc<RefCell<T>> gets you Python's "shared mutable objects everywhere" semantics. It works, but if you find yourself writing it a lot, you're probably fighting the language instead of restructuring the data (see section 14).

11. Concurrency without data races

The aliasing-XOR-mutation rule turns out to be exactly the condition for avoiding data races. Two automatically derived marker traits extend it across threads:

  • Send: ownership of this value can be moved to another thread.
  • Sync: &T can be shared between threads.

Rc is neither, because its refcount isn't atomic. Arc is both, provided T is. RefCell isn't Sync, but Mutex is. You never implement these traits by hand in normal code. The compiler infers them from the fields, and APIs like thread::spawn require them:

use std::sync::{Arc, Mutex};
use std::thread;

let counter = Arc::new(Mutex::new(0u64));
let handles: Vec<_> = (0..8).map(|_| {
    let c = Arc::clone(&counter);
    thread::spawn(move || {
        for _ in 0..1000 { *c.lock().unwrap() += 1; }   // lock guard unlocks on drop
    })
}).collect();
for h in handles { h.join().unwrap(); }
println!("{}", *counter.lock().unwrap());   // 8000

// Scoped threads may borrow from the enclosing stack frame: no Arc needed.
let data = vec![1, 2, 3, 4];
let (left, right) = data.split_at(2);
let (a, b) = thread::scope(|s| {
    let h1 = s.spawn(|| left.iter().sum::<i32>());
    let h2 = s.spawn(|| right.iter().sum::<i32>());
    (h1.join().unwrap(), h2.join().unwrap())
});

Notice that Mutex<T> owns the data it protects. In C the mutex sits next to the data and the locking discipline is a comment. In Rust you can't reach the data without holding the lock, and the lock is released when the guard goes out of scope. Swap Arc for Rc in the code above and you get a compile error (Rc<…> cannot be sent between threads safely), not a heisenbug. For data parallelism, the rayon crate turns .iter() into .par_iter(). For message passing, there's std::sync::mpsc (and crossbeam).

Async will look familiar from JS and Python: async fn, .await, and the same "function colouring". There are two key differences:

  1. Futures are lazy. Calling an async fn returns a state machine (a struct) and runs nothing until something polls it. A JS Promise, by contrast, starts running immediately.
  2. There's no built-in event loop. You choose a runtime library, almost always tokio, and mark main with #[tokio::main].

Async Rust is powerful, but it's the roughest part of the language. Use it for network servers and clients. Use threads for CPU-bound work.

12. unsafe and FFI

unsafe { … } doesn't switch off the borrow checker. It unlocks five specific operations the compiler can't verify: dereferencing raw pointers (*const T, *mut T), calling unsafe functions (including all foreign functions), accessing mutable statics, implementing unsafe traits, and reading union fields. Inside the block, you are responsible for upholding the invariants, exactly as in C.

The idiom is to keep a small unsafe core behind a safe API whose types make misuse impossible. Vec, HashMap and Mutex are all built this way. Most application code contains no unsafe at all.

Talking to C is straightforward:

use std::ffi::{c_char, c_int, CStr};

unsafe extern "C" {                        // declare C functions (edition 2024 syntax)
    fn abs(x: c_int) -> c_int;
}

#[unsafe(no_mangle)]                       // export a C-ABI symbol
pub extern "C" fn rust_strlen(s: *const c_char) -> usize {
    if s.is_null() { return 0; }
    unsafe { CStr::from_ptr(s) }.to_bytes().len()
}

fn main() { println!("{}", unsafe { abs(-3) }); }

#[repr(C)] gives a struct C layout. bindgen generates Rust declarations from C headers, and cbindgen generates headers from Rust. For your other two languages, PyO3 + maturin builds Python extension modules (this is how pydantic-core, polars and orjson are built), and wasm-bindgen / napi-rs let TypeScript call into Rust compiled to WebAssembly or to a native Node addon.

13. Modules, visibility, tests

// src/main.rs
mod geometry;                    // loads src/geometry.rs (or src/geometry/mod.rs)
use geometry::{Point, area};     // bring names into scope

// src/geometry.rs
pub struct Point { pub x: f64, pub y: f64 }   // everything is private unless `pub`
pub fn area(/* … */) -> f64 { 0.0 }
fn helper() {}                                // private to this module
pub(crate) fn internal() {}                   // visible within the crate only

#[cfg(test)]                     // compiled only for `cargo test`
mod tests {
    use super::*;
    #[test]
    fn origin_is_zero() { assert_eq!(Point { x: 0.0, y: 0.0 }.x, 0.0); }
}

A package (one Cargo.toml) contains one or more crates: a library (src/lib.rs) and/or binaries (src/main.rs, src/bin/*.rs). Unit tests live next to the code. Integration tests go in tests/. Code examples in /// doc comments are compiled and run as tests too, so the docs can't silently go stale. Workspaces group several packages that share one lockfile, like a monorepo.

14. Getting along with the borrow checker

Every newcomer goes through a phase of fighting the compiler. These habits shorten it:

  • Read the whole error. rustc errors are unusually good. They point at all three relevant places (where the borrow is created, where it conflicts, and where it is later used) and often suggest the fix.
  • Clone first, optimize later. A .clone() of a small String costs less than an hour of your time. Profile before removing clones.
  • Structs own, functions borrow. Put String and Vec<T> in structs. Take &str and &[T] as parameters.
  • Use indices instead of pointers for graphs. Doubly linked lists, trees with parent pointers and general graphs fight single ownership. Store nodes in a Vec<Node> and link them by usize index (an "arena"), or reach for a crate such as petgraph or slotmap. Don't make a linked list your first project. There's a whole book on why.
  • Borrow fields, not self. A method taking &mut self locks the entire struct. If you need to mutate one field while reading another, borrow them directly (let (a, b) = (&mut self.x, &self.y);) or split the struct.
  • Shorten borrows. Since a borrow ends at its last use, moving a computation earlier, or copying a small value out (let n = v.len();), often fixes the error.
  • Run cargo clippy. It teaches idioms faster than reading does.
